# E1.1b — SEARCH/USE service feasibility and optimization

**Date:** 2026-09-05 · **Status:** optimization validation in progress; all completed four-client configurations failed the 400 ms gate; no production sign-off.
**Scope:** local HTTP service, resident SKILLRET encoder, 6,006-skill index, revision delivery and failure/recovery evidence.
**Plan:** [MVP](../../MVP.md), [E1 closure](E1-closure-plan.md), [ADR-0023](../../adr/ADR-0023-search-use-service-and-measured-utility.md).

The product owner requested immediate service validation before dependent E2/E6 work and revised the whole-client target from 300 to **p95 <400 ms**, including four simultaneous fresh clients. Historical 300 ms measurements remain unchanged. Cache, native ranking and pipeline changes improved completed measurements, but have not met that full target. Validation of an owned spawned GPU worker is the next experiment, not an achieved result.

## Measurement contract

- Model: `ThakiCloud/SKILLRET-Embedding-0.6B`, revision `0e10886e80a0aacc9efddc28282a258e2ab7eae1`, fp16 GPU inference; no reranker.
- Corpus: 6,006 SKILLRET test skills, revision `a050ad233a504a43135bafe8cdf45574052b5729`; 1024-dimensional int8 document vectors. Startup verifies every row against its source-text/model float cache.
- Workload: 200 distinct frozen public DEV query texts, selected deterministically without labels; profile `hook`, node `_root`. The document pool differs from those DEV labels: this is latency/parity evidence, not retrieval quality.
- Every hybrid query reaching the encoder runs `_encode_uncached`; no query-vector file or response cache is used. Timed-out requests may still complete inference.
- Hardware: RTX 4090, 24,564 MiB; Intel Core i7-10700K, 16 logical CPUs; Ubuntu WSL2, Python 3.12.3. This shared workstation is not an isolated production host; environment artifacts record observed load and GPU state.
- Percentiles use nearest rank. Failures remain in all-attempt denominators. Never add/subtract stage p95s to infer end-to-end p95.
- HTTP includes client setup, serialization, transfer, decoding and synchronous local JSONL logging. Fresh-client time adds Python startup/imports, token-file read and exit. It excludes the real harness, WAN, TLS, production IAM and a separately deployed GPU-worker network hop.
- Primary runs use a 1000 ms server-stage deadline to expose tails. Separate bursts use 400 ms; transport timeout is 5 s. These deadlines do not preempt a model forward or impose hard whole-client cancellation.
- The complete local gate requires 200/200 successes and p95 <400 ms in primary HTTP c1/c4 and fresh c1, plus burst HTTP c4 and fresh c4. Per-attempt strict `<400` counts are reported separately. Different burst deadlines/concurrency preclude comparative speedups.

## Implemented optimizations and rejected thread setting

- `--optimized`: precomputes exact BM25 term/document contributions before readiness, then applies query frequency and visibility. Integer rounding, zero-score keys and hybrid ranks are preserved. This is a corpus cache, independent of the probe queries. A resident int64 dense matrix removes repeated document-matrix allocation/casting.
- `--native-dense-rank`: C++17 replaces only dense ordering, comparing signed dot-squared/norm cross-products with `__int128`, then descending dot and lexicographic URN ties. Guarded bounds `abs(dot) <= 2^40`, `0 < norm <= 2^40` keep intermediates safe; unsupported inputs use the original Python comparator. Compilation/loading occurs before readiness; source/compiler/library SHA and native/fallback counters are recorded. The supplied Router instance is adapted without patching shared CLI globals.
- `--pipeline`: separate encoder and Router locks allow the next single-query GPU forward to overlap prior CPU routing. Each request owns its vector; Router mutation remains serialized. This is not batching or a separate process.
- `--gil-switch-ms 0.5`: separately tested CPython scheduling ablation; the other configurations preserve the interpreter default. It changed neither ranking formulas nor the model. Its completed run failed the gate and did not support adopting this setting.

A [paired 40-query encoder experiment](validation/e11b-encoder-threads.json) did not support reducing PyTorch threads from 16 to 1: encoder p95 was 76.0 versus 87.0 ms respectively; paired median difference (1 minus 16) was -0.26 ms. Float and int8 vectors matched exactly in 40/40 pairs. The following HTTP runs retain 16 threads.

The shared product CLI was not changed by these service adapters. `--cli-path` hashes and executes frozen source bytes. Runtime adapter hashes and flags are in environment artifacts. The native+pipeline result changes two mechanisms together; its gain cannot be attributed to C++ alone.

After each native primary probe, counters showed 605 native calls, zero fallback/empty calls, and one model load. ## Remaining CPU work: diagnostic profile

The [40-query CPU profile](validation/e11b-candidate-cpu-profile.json) uses a fixed document vector as the query vector, without GPU inference. Uninstrumented candidates p50/p95 was 31.4/42.6 ms. Component timings from a separate decomposition are diagnostic, not end-to-end predictions:

| Component | Mean / p95 ms |
|---|---:|
| Cached BM25 accumulation | 11.68 / 16.74 |
| Dense dot + Python dictionary | 7.92 / 9.72 |
| Native dense ordering including Python marshalling | 4.64 / 5.11 |
| Policy inside candidates | 3.17 / 3.60 |
| Additional outer policy | 3.27 / 3.56 |

The profile still shows Python dictionary work, marshalling and duplicate policy traversal; warming the GPU alone cannot remove these costs. `cProfile` adds overhead, so its cumulative totals are not latency estimates. The profile motivates testing separation of CPU routing and encoder dispatch, but does not prove GIL contention caused the observed c4 tail or that another process will pass.

## Completed delivery/failure checks and unmeasured product gates

All four primary probes completed 20/20 repeated USE requests for one selected revision, checking body checksum and requested revision. USE p95 was 30.1/26.2/20.6/20.5 ms for reference/cache/native+pipeline/GIL. Each rejected a missing revision with HTTP400. Runtime checks passed invalid token401, oversized body413, stale revision409, 1 ms deadline504 and a subsequent successful SEARCH; see raw primary results and the earlier [sparse smoke](validation/e11b-sparse-fault-smoke.json). This is recovery after rejected requests, not proof of recovery from a killed GPU worker.

The server's `use_hydrated` event means a revision response was prepared. Probe checksum verification proves delivery to this probe; neither establishes hydration into an agent harness, observed skill use, usability or task utility. SEARCH reports `composition.status:not_evaluated`. Tenant IAM, dependency closure/caps, durable events, actual local BM25 fallback and client authorization leases remain outside this spike. The controlled fallback helper is not shipped CLI integration. Local success would still leave real-harness/network/TLS/IAM, 30k scale, sustained load, update/revocation and usefulness gates open.

Reproduction: [spike README](../../../tools/serve_spike/README.md) documents pinned source, startup, primary/burst probes and `compare.py`; each comparison includes input SHA and each environment records actual startup arguments/source hashes. Preserve these artifacts when rerunning revised code.
