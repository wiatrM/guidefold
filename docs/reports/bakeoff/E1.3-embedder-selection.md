# E1.3 (phase 2): bake-off report over the golden set, and the `w_dense` gate decision

Every retrieval arm the MVP has proposed, run over the same 220-query golden set
(`tests/golden/*.yaml`), reported per stratum and overall, feeding the `w_dense` ship/no-ship
decision written into [ADR-0020](../../adr/ADR-0020-two-tier-dense-retrieval.md). Phase 1
(`tools/bakeoff/README.md`) pinned the models, built the tokenizer/distillation pipeline, and
ran each arm on one sample query; this report is the missing piece of the E1.3 acceptance
criterion — "one report; model + HF commit SHA + license pinned; weights copied to GCS" — the
report itself, and the evidence that picks the embedder.

## Methodology

**Reused, not reimplemented.** Every metric below is computed by `tools/eval/metrics.py`
(`evaluate`, `by_category`) — the same module the golden-set CI runner uses. This report adds no
new metric definitions.

**One ranked list per arm, no separate "injection order".** `docs/reports/golden/README.md`
documents that the *shipped* `Router` class produces two different orderings — `Router.score`
(retrieval: score-descending, feeds hit@1/recall@8/nDCG@10) and `Router.select` (injection:
node-depth order, root-most first, feeds completeness@4/distractor_rate@4) — and that conflating
them previously understated hit@1 by 64 points. **That distinction does not apply to the arms in
this report.** B0–B6 each return exactly one score-descending ranked list; none of them has a
`Router.select`-style re-ordering step. Every metric in every table below is read from that single
list, sliced to the k each metric needs (top 8 for recall@8, top 10 for nDCG@10, top 4 for
completeness@4/distractor_rate@4). There is nothing analogous to injection order to conflate here.

**A naming collision, flagged so it doesn't confuse a future reader.** `tools/bakeoff/arms.py`
already defines a function called `arm_b0`, used in phase 1's sample-query smoke test. That
`arm_b0` calls the *current* `Router` (`cli.Index.build()` + `cli.Router.route()`) — it is **not**
this report's B0. This report's B0 (per the coordinator's brief) is the *original*, pre-Router-split
scope-only CLI at commit `984d08c`, extracted verbatim from git and run as a subprocess
(`tools/eval/compare_b0.py::run_b0`, reused unchanged from the M2 comparison in
`docs/reports/golden/README.md`). The current Router 0.1's own golden-set numbers are not
recomputed in this report — they are carried forward here for context, since they were the
original evidence for the Recall@8-saturation finding this report leans on throughout:

| metric | B0 | Router 0.1 | Δ |
|---|---:|---:|---:|
| hit@1 | 0.6839 | 0.8736 | **+18.97 pp** |
| nDCG@10 | 0.7959 | 0.8880 | **+9.21 pp** |
| completeness@4 | 0.9023 | 0.9713 | **+6.90 pp** |
| recall@8 | 0.9310 | 0.9339 | +0.29 pp |

(Router 0.1 is a different system from every B0–B6 arm in this report — it is the *shipped*
Router with its dual-ordering + RRF-of-existing-signals design, not a bake-off arm. It is included
here only because its own Recall@8 gain over B0, +0.29pp against a +18.97pp hit@1 gain over the
same baseline, is the clearest existing evidence that Recall@8 stops discriminating once a ranker
is already good on this fixture — exactly the caution this report applies to the B5-vs-B1/B4 gate
below.)

**Abstention is not implemented by any arm in this report.** All of B0–B5 return a ranked list
unconditionally — none has a confidence threshold that can produce an empty ranking. This mirrors
the shipped Router's own documented weakness ("RRF is rank-based, so any rank-1 hit receives a
near-constant high score... a magnitude threshold cannot discriminate against that" —
`docs/reports/golden/README.md`), reproduced independently here in every arm's JSON output:
`abstention_precision` is `null` and `coverage` is `1.0` throughout, because `tp + fp = 0` (nothing
ever abstains). On the `no_applicable` stratum (44 cases, the correct answer is silence),
`hit@1`/`recall@8`/`nDCG@10` are therefore undefined for every arm; `distractor_rate@4` is the only
ranking-adjacent number that stratum can report here.

**Recall@8 is saturated on this fixture.** 26 skills, 8–18 visible candidates per query. B0 already
scores 0.9310 Recall@8, leaving at most 6.9 points of headroom — the coordinator's caution, echoing
`docs/reports/golden/README.md`'s finding for the Router-vs-B0 comparison. Every table below reports
hit@1 and nDCG@10 alongside Recall@8 for exactly this reason; the gate section explicitly checks the
same threshold against all three rather than defaulting to whichever looks best.

**This report's numbers are a single GPU pass, not a CPU run patched with a missing row.** An
earlier attempt ran every dense arm on CPU and got real, complete measurements for B0, B1, B2a,
B2b, B3a, B4 and B5 — but B3b (SKILLRET-Embedding-0.6B) was still mid-encode, competing on CPU with
a concurrently-running reranker process, when the session hosting it was interrupted. The
interruption wiped the torch venv, the ~7GB Hugging Face model cache, and the in-progress
`.bakeoff-cache` encodings for B3b along with it, and re-encoding on CPU would have cost hours.
Rather than ship that partial run with B3b marked "not measured," this report was **re-run
end-to-end on an RTX 4090** once GPU compute and a local, offline model mirror became available
(hardware in full below). Every arm in every table in this report — B3b included — is one fresh
measurement from that single GPU pass; none of the numbers below are carried forward from the
interrupted CPU attempt. `tools/bakeoff/encode.py` now resolves each model against a local
snapshot directory (`/home/mike/.cache/guidefold/models/<org>__<name>/<hf-commit-sha>/`,
`HF_HUB_OFFLINE=1`, no network touched) and runs at `torch.float16` on `cuda` instead of
`torch.float32` on `cpu`; the per-text disk cache is now keyed by device+dtype as well as by text,
so a CPU-fp32 cache entry and a GPU-fp16 cache entry for the same string never collide or get
silently mixed within one arm's result.

**A GPU number is not always bit-identical to the earlier CPU number for the same arm, and that is
expected, not a bug.** Floating-point reductions are not bit-reproducible across hardware or batch
size — different accumulation order, different rounding — which is exactly the caveat the
coordinator's brief raised in advance. Concretely: B0 and B1 do no floating-point ranking math (a
fixture-tree scope scan, and integer/float BM25 respectively) and their numbers are unchanged
between the two attempts, letter for letter. B2a and B2b matched the earlier CPU-fp32 run's
hit@1/recall@8/nDCG@10 to 4 decimal places; only completeness@4 moved (≤0.6pp on B2a — a rank-4 tie
flipping under fp16). B3a, B4 (which distills from B3a's teacher) and B5 (which is built on B4)
moved by a few tenths of a point up to about a point and a half on hit@1/nDCG@10 — small, real, and
consistent with this caveat, not a measurement error. None of this is, or is presented as, part of
the runtime determinism claim, which lives entirely in the integer-only `words.bin`/`vectors.i8`
CLI path that this report never touches; every number below is offline evidence for *choosing* an
embedder, nothing more.

(Ubuntu 2.39-0ubuntu8.8), CPython 3.12.3. B0 and B1 ran on CPU only (no torch import — see

installed PyTorch wheel (`torch==2.11.0+cu128`) is itself built against the CUDA 12.8 runtime,
which is what actually executes — both figures are reported since they answer different questions

`transformers==5.16.1`. Every dense arm ran `device="cuda"`, `dtype=torch.float16`,
`torch.no_grad()`, `batch_size=64` (sentence-transformers models sort inputs by length internally
before batching to minimise padding; the one hand-rolled raw-`transformers` path, B3a, does this

## The gate decision (ADR-0020)

> ship `w_dense > 0` only if BM25 + static dense beats the better BM25 arm by **≥ 3 percentage
> points Recall@8 with no regression on the sibling-ambiguity or no-applicable strata**. Otherwise
> the artifact ships `w_dense = 0` and the report says so.

The candidate is B5 (B1 + B4 via RRF); the arm it must beat is `max(B1, B4)` on Recall@8.

**Overall:**

| | B1 | B4 | better(B1,B4) | B5 | B5 − better |
|---|---:|---:|---:|---:|---:|
| recall@8 | 0.9799 | 0.9320 | 0.9799 (B1) | 0.9923 | **+1.24 pp** |
| hit@1 | 0.8736 | 0.6494 | 0.8736 (B1) | 0.8276 | **−4.60 pp** |
| nDCG@10 | 0.9087 | 0.7587 | 0.9087 (B1) | 0.8833 | **−2.54 pp** |

The primary criterion fails outright: B5 gains only **1.24 percentage points** of Recall@8 over
the better BM25 arm (B1), against a 3-point bar. And per the coordinator's caution about
saturation, the same comparison against hit@1 and nDCG@10 — the two metrics that still
discriminate on this fixture — doesn't just fail to clear a bar, it **regresses**: B5 is 4.60
points worse than B1 alone on hit@1 and 2.54 points worse on nDCG@10. Fusing in the static-dense
channel does not help; on this measurement it actively hurts the metrics that most reliably
reflect ranking quality here.

**Per-stratum regression check (sibling_ambiguity, no_applicable):**

| Stratum | Metric | B1 | B5 | Δ |
|---|---|---:|---:|---:|
| sibling_ambiguity | recall@8 | 1.0000 | 1.0000 | 0.00 pp |
| sibling_ambiguity | hit@1 | 0.9091 | 0.7424 | **−16.67 pp** |
| sibling_ambiguity | nDCG@10 | 0.9584 | 0.8844 | **−7.40 pp** |
| no_applicable | distractor_rate@4 (only ranking-adjacent metric defined here) | 0.4318 | 0.4318 | 0.00 pp |

This is the sharpest finding in the whole report, and it is *stronger* on real GPU numbers than it
was on the interrupted CPU attempt's partial data. `sibling_ambiguity` — the stratum ADR-0020 names
by name as the one to protect — shows **no** movement on Recall@8 (both arms already at the
ceiling, 1.0000) but a **16.67-point collapse in hit@1** and a 7.40-point drop in nDCG@10 once B4's
static-dense vote is fused in via RRF. Recall@8 could not have caught this: it was already
saturated at 1.0 for both arms on this stratum, so the gate's literal Recall@8-only wording would
have silently passed a candidate that measurably regresses the exact failure mode it exists to
guard against. `no_applicable` shows no comparable regression on the one metric this stratum can
report (distractor_rate@4 is unchanged).

**Gate decision: FAIL. Ship `w_dense = 0`.**

The dense channel, fused via RRF into B5 exactly as ADR-0020 proposes to gate it, does not earn
its complexity on this 26-skill corpus. It buys a little over a point of Recall@8 — a metric
already 98% saturated by BM25 alone — at the cost of measurable regressions on hit@1 and nDCG@10,
the metrics that still discriminate here, and specifically a 16.67-point hit@1 collapse on exactly
the stratum the gate names by name. This is the honest outcome the coordinator's brief anticipated
as "a completely acceptable result, preferred over a tuned-up number," and it is what the numbers
show — now on a full GPU re-run with every arm measured, not a partial one. The static-dense table
(`words.bin`/`vectors.i8`) still ships in the index artifact as ADR-0020 designs it — building it
costs nothing at hook-query time and it may earn its weight on a larger corpus — but `w_dense` in
the shipped manifest should be `0` until then.

### Why this is plausible, not just a bad measurement

RRF (k=60) fuses two rankers by rank position, not by score magnitude. B4's static table is a
256-dim mean-pooled distillation of a 0.6B teacher — weakest exactly where ADR-0020 predicts it
would be ("static mean-pooled vectors are weakest exactly where the golden set is heaviest —
sibling ambiguity, multi-skill"). When B4 places a plausible-but-wrong sibling skill at a
competitive rank, RRF's rank-based fusion lets that vote pull down a case B1 alone would have
gotten right at rank 1 — which is exactly the shape of the hit@1 regression measured above.

### If the pilot corpus later justifies dense

Irrespective of the gate, the question of which teacher to pick *if* a larger corpus (~200 skills,
per `docs/reports/golden/README.md`'s Recall@8 recommendation) later makes the dense channel worth
its complexity is now answerable with all four teachers measured (see the next section for the
full comparison): **SKILLRET-Embedding-0.6B (B3b)** leads on hit@1 and nDCG@10 — the two metrics
that discriminate on this fixture — while **Qwen3-Embedding-0.6B (B2a)** leads narrowly on
Recall@8, the metric this report has repeatedly shown is close to saturated here. On the evidence
actually available, B3b is the stronger pick for a future dense channel, with the caveat that a
26-skill fixture is a small basis for ranking two very close scores (B3a and B3b tie on Recall@8 to
4 decimal places) and this question should be revisited on the ~200-skill pilot corpus before it is
treated as final.

**SKILLRET-Embedding-0.6B (B3b) wins on quality, on the full evidence — not Qwen3 (B2a).** This is
a reversal from what a partial run (missing B3b) would have shown: B3b leads every other teacher on
hit@1 (+5.75pp over B2a, the next best) and nDCG@10 (+3.36pp over B2a). Qwen3-Embedding-0.6B (B2a)
keeps a narrow lead on Recall@8 (0.9856 vs. B3b's and B3a's tied 0.9799, a **0.57pp** gap) — but
this report has already established Recall@8 as close to saturated on this 26-skill fixture
(≤6.9pp of headroom above B0's own 0.9310), so a 0.57pp Recall@8 edge is a much weaker signal here
than a 5.75pp hit@1 and 3.36pp nDCG@10 deficit. Weighed on the two metrics that actually
discriminate on this fixture, **SKILLRET-Embedding-0.6B is the evidence-based teacher pick**,
narrowly ahead of Qwen3-Embedding-0.6B; both skill-tuned candidates (B3a, B3b) also comfortably
beat the two generic ones except on Recall@8, where the generic Qwen3 model happens to have the
edge. Notably, this is *not* simply "skill-tuned beats generic" either — SkillRouter-Embedding-0.6B
(B3a), the other skill-tuned candidate, is the *weakest* of the three non-bge-m3 teachers on hit@1
and nDCG@10, so which specific skill-tuned model was used to build the skill-retrieval fine-tune
matters at least as much as whether one was used at all.

Because B3a (SkillRouter-Embedding-0.6B) is also B4's distillation teacher, its own embedding-space
numbers can be compared directly against the static table distilled from it — the gap is the cost
paid for quantizing a 0.6B teacher down to a shippable 256-dim int8 table, independent of BM25/RRF
entirely:

| | B3a (teacher, full embedding) | B4 (distilled static table) | Cost of distillation |
|---|---:|---:|---:|
| hit@1 | 0.7874 | 0.6494 | **−13.80 pp** |
| recall@8 | 0.9799 | 0.9320 | **−4.79 pp** |
| nDCG@10 | 0.8589 | 0.7587 | **−10.02 pp** |

Distilling B3a down to B4's 256-dim int8 static table costs a substantial 13.80 points of hit@1 and
10.02 points of nDCG@10 — the static table is a meaningfully weaker signal than its own teacher.
That gap is a large part of *why* B5 (B1 fused with B4) underperforms B1 alone in the gate section
above: B4 is not "the teacher, compressed for free" — it is a materially degraded version of it,
and RRF fusion cannot recover quality the distillation step already gave up. (This report does not
have a distilled table built from B3b's teacher space to compare the same cost for the actual
quality-winning teacher; `DEFAULT_STUDENT_TEACHER` in `arms.py` is still SkillRouter-Embedding-0.6B,
a phase-1 default the coordinator's brief explicitly did not ask this report to change. If B3b is
adopted as the teacher for a future dense channel, its own distillation cost should be measured
before assuming it distills as cleanly as B3a did.)
