## 2. Tożsamość i autoryzacja

Każde żądanie `/api/v1/*` i `/v1/*` rozstrzyga `Principal` **przed** handlerem, z bazy, bez cache między żądaniami (bramka 1). Struktura odpowiada `services/search/internal/mgmt/principal.go`.

| Pole `Principal` | Typ | Znaczenie |
|---|---|---|
| `UserID` | uuid, puste dla tokenu maszynowego | Człowiek stojący za żądaniem |
| `OrgID` | uuid | Tenant żądania; jedyne źródło `tenant` dla schematu `gf` |
| `RepoID` | text, opcjonalne | Ustawione, gdy token jest związany z jednym repo |
| `Role` | `owner`\|`member`\|puste | Rola wynikająca z membership, nie z claimu klienta |
| `Scopes` | []text | Zakresy tokenu; sesja i token osobisty mają zakresy dostawy z definicji |
| `Source` | `session`\|`personal`\|`installation`\|`ci`\|`operator` | Skąd pochodzi tożsamość |
| `TokenID`, `SessionID`, `CSRF` | text | Identyfikatory do audytu, idempotencji i double-submit |

| Źródło | Nośnik | Nadaje | Zakresy |
|---|---|---|---|
| Sesja | cookie `gf_session`, HttpOnly, Secure (wyłączane tylko `GUIDEFOLD_INSECURE_COOKIES=true` lokalnie), SameSite=Lax, TTL 7 dni, rekord w `gfm.sessions` z `revoked_at` | Wszystkie operacje zgodne z rolą | wszystkie (domyślnie) |
| Token osobisty | `Authorization: Bearer gf_…` | Działa w imieniu użytkownika i jego membershipów | `user`, `search`, `use`, `events` |
| Token instalacji | `Authorization: Bearer gf_…` | Org (+ opcjonalnie repo) | podzbiór `search use events`; nigdy `import`, `publish`, `membership` |
| Token CI | `Authorization: Bearer gf_…` | Org (+ repo) | podzbiór `validate import generate`; nigdy `publish`, `membership` ani zakresy dostawy |
| Operator (legacy) | dotychczasowy bearer token z konfiguracji | Zachowuje obecne zachowanie testów `/v1/*` | wszystkie w obrębie skonfigurowanego tenant/repo |

Dla `/v1/search`, `/v1/use` i `/v1/events:batch` schemat JSON zostaje przy `1.1` bez zmian (schemat harnessu odrzuca nieznane pola najwyższego poziomu), więc wybór organizacji i repozytorium dla principali `session` i `personal` nie może wejść do ciała żądania — pochodzi z nagłówków `X-Guidefold-Org: <org_id|slug>` i `X-Guidefold-Repo: <repo_id>` (nagłówki opisane w §3). Kolejność rozstrzygania dla tych trzech endpointów: wiązanie tokenu (org, a opcjonalnie repo, gdy token instalacji lub CI jest do nich związany) > nagłówki `X-Guidefold-Org`/`X-Guidefold-Repo` > `workspace.repo_id` z ciała żądania (1.1) > jedyne membership principala albo jedyne repo organizacji, gdy wcześniejsze źródła milczą. Nagłówek sprzeczny z wiązaniem tokenu instalacji kończy się `403 organization_not_permitted` (org) albo `403 repository_not_permitted` (repo). Token operatora (legacy) nie czyta tych nagłówków — zachowuje dotychczasowe tenant/repo ze zmiennych środowiskowych.

Zakresy tokenu CI rozszerzono z samego `validate` do podzbioru `validate import generate`, bo `guidefold extract` w CI (§5.6, CONVENTIONS `extract`) musi zaimportować drzewo i zlecić generowanie propozycji. Zakresy tokenu instalacji **nie zmieniają się**: adapter nadal dostaje wyłącznie podzbiór `search use events`. Token CI nadal nie może publikować ani zmieniać membership — propozycje wymagają decyzji właściciela, a publikacja osobnego joba. Żądanie z zakresem spoza wydanego tokenu to `403 insufficient_token_scope` z nazwą brakującego zakresu w `details.required_scope`; nazwa zakresu nigdy nie niesie sekretu.

Reguły:

- Membership i ważność tokenu są sprawdzane **przy każdym żądaniu**. Odwołanie działa na API natychmiast; 60 s z U3.4 dotyczy wyłącznie cache UI (§9).
- Dostęp do organizacji, której principal nie jest członkiem, oraz do organizacji nieistniejącej daje **identyczny** `403 forbidden` bez `details`. Nigdy 404; 404 występuje wyłącznie wewnątrz własnej org.
- Member czyta, owner mutuje. Wyjątki: feedback do skilla (member), akceptacja zaproszenia (zapraszany).
- Tokeny są przechowywane jako SHA-256; sekret pokazywany jednorazowo w odpowiedzi tworzącej. Sekret nigdy nie trafia do URL, logu, telemetrii ani `details`.
- Tokeny (personalny, instalacji, CI) są w MVP wyłącznie odwoływalne: `gfm.tokens` nie ma kolumny `expires_at` (YAGNI); jedyną drogą unieważnienia jest `revoked_at`. Dotyczy to również tokenu osobistego wydanego przez device flow — nie różni się od innych tokenów osobistych. `POST /api/v1/auth/logout` odwołuje wyłącznie sesję (cookie `gf_session`); token osobisty CLI odwołuje się osobno, jawnym `guidefold logout`, więc wylogowanie z UI nigdy nie zrywa niepowiązanej sesji CLI.
- Mutacje z sesji wymagają nagłówka `X-CSRF-Token` równego `csrf_token` sesji (double submit). Tokeny bearer nie podlegają CSRF, bo przeglądarka ich nie dosyła automatycznie.
- Device flow: `POST /api/v1/auth/device` bez uwierzytelnienia zwraca `device_code`/`user_code`; zatwierdzenie wymaga sesji i CSRF; wymiana na token zwraca token osobisty o zakresie `user`. Brak sekretu klienta OAuth.
- Łączenie tożsamości jest jawne: `POST /api/v1/me/identities/link/start` wiąże `state` z bieżącą sesją. Sam zgodny e-mail nigdy nie łączy kont automatycznie; powstaje osobny użytkownik, a `GET /me` zwraca `link_suggestions`.
- Dostawca: `GUIDEFOLD_AUTH=dev|workos`. Provider `dev` jest wyłączony, dopóki nie zostanie ustawiony jawnie. Klucz WorkOS pochodzi z `WORKOS_API_KEY_FILE` i nigdy nie jest logowany. Nie żądamy zakresów OAuth do kodu repozytorium — z jednym jawnym wyjątkiem: połączenie GitHub w WorkAuthKit korzysta z danych OAuth Aplikacji GitHub Guidefold z włączonym „Return OAuth tokens”, więc `POST /user_management/authenticate` może nieść `oauth_tokens` (`provider`, `access_token`, `refresh_token`, `expires_at`, `scopes`) obok użytkownika. `identity/workos.go` parsuje to pole tolerancyjnie (nieoczekiwany kształt nigdy nie przerywa logowania) i **nie używa, nie zapisuje ani nie loguje** tokenu — konsumuje go dopiero osobna zmiana przez `internal/ghapp`.
- **Stany pośrednie AuthKit.** `POST /user_management/authenticate` WorkOS może odpowiedzieć jednym z czterech rozpoznawanych stanów zamiast użytkownikiem: `email_verification_required`, `organization_selection_required`, `mfa_enrollment`, `mfa_challenge` (każdy niesie `pending_authentication_token`; pierwszy dodatkowo `email`). Żaden z nich nie jest raportowany jako `provider_unavailable` — to byłby fałszywy obraz stanu dostawcy. Tylko `email_verification_required` ma własny przepływ (niżej); pozostałe trzy kończą się przekierowaniem na `/login?auth=<kod>` z jednym zdaniem w konsoli — rozpoznane, ale świadomie niebudowane. Inny, nierozpoznany stan (np. `sso_required`, wyzwania Radar) trafia do dotychczasowego `provider_unavailable`.
  **`email_verification_required`.** `GET /api/v1/auth/callback` otwiera nowy, jednorazowy, krótko żyjący wiersz `gfm.auth_states` (rodzaj `email_verification`, ten sam mechanizm co `login`/`link`/`github_install` — cookie `gf_auth_state`, `expires_at` = `AuthStateTTL`), niosący `pending_token` i `pending_email` WorkOS oraz to, co już udowodnił oryginalny claim (`provider`, `user_id` przy `link`, `return_to`), po czym przekierowuje na `/login/verify-email?email=<maska>` — nigdy z surowym adresem, tokenem ani sekretem stanu w adresie. `pending_token` jest jedynym sekretem w tym schemacie przechowywanym **jawnie**, nie jako SHA-256 (odstępstwo od reguły pakietu `identity`): musi wrócić do WorkOS dosłownie przy kroku kodu, więc nie da się go zredukować do skrótu. Uzasadnienie: krótki TTL (10 min), jednorazowość, nigdy nie opuszcza serwera, nigdy nie jest logowany — nie sięga po szyfrowanie w stylu `gfm.org_credentials` (ADR-0045), bo to niewspółmierne do 10-minutowego okna. `POST /api/v1/auth/verify-email` (zwykła trasa JSON, nie cel nawigacji: konsola wywołuje ją przez `fetch`) czyta `gf_auth_state` bezpośrednio jako klucz wiersza — nie ma osobnego `state` odsyłanego przez wywołującego — rezerwuje jedną próbę w tej samej transakcji, po czym woła grant `urn:workos:oauth:grant-type:email-verification:code`. Błędny kod **nie** kasuje wiersza (musi zostać powtarzalny), tylko zwraca `email_code_invalid`; wiersz jest kasowany i raportowany dopiero przy wygaśnięciu (`expired_state`) albo po `EmailVerificationMaxAttempts` (5) błędnych próbach (`email_code_attempts_exceeded`). WorkOS nie dokumentuje osobnych kodów błędu dla złego/wygasłego kodu na tym grant, więc Guidefold **sam definiuje** te trzy wyniki z własnego wiersza (TTL, licznik prób), zamiast zgadywać nieudokumentowany kształt odpowiedzi WorkOS. Sukces kasuje wiersz, kończy logowanie tą samą ścieżką co `handleCallback` (`signIn`/`startSession`) i odpowiada `{schema_version, return_to}` zamiast przekierowania, bo `fetch` nie podąża za `302` do nowego dokumentu. WorkOS nie eksponuje odrębnego „resend” dla tego przepływu (sprawdzone w dokumentacji: `email_verification_required` niesie tylko `email`/`email_verification_id`, bez identyfikatora użytkownika, do którego dałoby się adresować osobne wysłanie) — konsola tego przycisku nie ma.

## 3. Koperta odpowiedzi, nagłówki, błędy, stronicowanie, idempotencja

Sukces zawiera `schema_version` (`mgmt-1` dla `/api/v1`, `1.1`/`1.2` dla `/v1`), `request_id`, a gdy dotyczy — `org_id`, `repo_id`, `snapshot_id`. Błąd ma zawsze kształt:

```json
{"error": "<snake_case_code>", "message": "…", "request_id": "…", "details": {…}}
```

`details` jest opcjonalne, maszynowe (np. `{"missing": ["sha…"]}`, `{"current_revision": "…"}`) i nigdy nie zawiera sekretów, e-maili ani treści repozytorium. Dla statusów ≥500 `details` jest usuwane, a przyczyna trafia wyłącznie do logu.

**`hint` (1.17.0).** Koperta błędu `/v1` może nieść dodatkowe, opcjonalne pole `hint:str?` — jedno zdanie po angielsku, adresowane do autora adaptera, mówiące, co wysłać zamiast tego. Jest addytywne i stałe dla danego kodu: nie zależy od żądania, nigdy nie niesie danych organizacji i nigdy nie zastępuje `error` (klient rozgałęzia się po kodzie, nie po tekście). Dziś ma je dokładnie jeden kod — `revision_mismatch` (§4.5).

| Nagłówek | Kierunek | Reguła |
|---|---|---|
| `X-Request-Id` | request/response | Klient może podać `[A-Za-z0-9_-]{8,64}`; wszystko inne jest zastępowane wygenerowanym. Zawsze w odpowiedzi i w polu `request_id`. |
| `Idempotency-Key` | request | Wymagany dla mutacji oznaczonych w §4; alternatywnie pole `idempotency_key` w ciele. Maks. 200 znaków. |
| `X-CSRF-Token` | request | Wymagany dla mutacji z sesji; równy `csrf_token` z `GET /api/v1/me`. |
| `X-Guidefold-Org` | request | Tylko `/v1/search`, `/v1/use`, `/v1/events:batch`: `org_id` (uuid) albo slug organizacji dla principali `session`/`personal`. Kolejność źródeł i sprzeczność z wiązaniem tokenu → §2. |
| `X-Guidefold-Repo` | request | Jak `X-Guidefold-Org`, dla `repo_id`. Sprzeczność z repo, do którego jest związany token instalacji, daje `403 repository_not_permitted`. |
| `Idempotent-Replay` | response | `true`, gdy zwrócono zapamiętaną odpowiedź zamiast wykonania pracy; `false` na trasach o odpowiedzi „na żywo" (poniżej), gdzie powtórzenie uruchamia handler ponownie. |
| `Retry-After` | response | Sekundy przy 429 i 503. Klient GET ponawia najwyżej 2 razy z backoffem, honorując tę wartość. |
| `Cache-Control: no-store` | response | Na każdej odpowiedzi `/api/v1` i `/v1`. Prywatne dane nie trafiają do trwałego cache. |
| `X-Content-SHA256` | response | Przy pobraniu dokładnych bajtów rewizji lub zasobu. |

### Stronicowanie, limity, idempotencja

- Listy zwracają `{items: [...], next_cursor: str|null}`. Kursor jest nieprzezroczysty, zawiera org, zasób, znormalizowane filtry i pozycję; kursor z innego zapytania to `400 invalid_cursor`. `limit` domyślnie 50, maksymalnie 100 (relacje: 200, mapa: start ≤100, twardy limit renderu 200 po stronie UI).
- Porządek list jest deterministyczny i zawiera klucz rozstrzygający: katalog `name asc, skill_id asc`; importy, propozycje i audyt `created_at desc, id desc`.
- Nieznana wartość filtru w katalogu **nie** cofa się do „All": odpowiedź to 200 z pustym `items` i `filters: {"scope": {"value": "…", "available": false}}`.
- Limity ciał: management JSON 1 MiB (`mgmt.DefaultBodyLimit`); blob `max_blob_bytes` 8 MiB; import `max_total_bytes` 100 MiB i `max_files` 100 000; `/v1/search`, `/v1/use` 16 KiB (1.1, bez zmian).
- Idempotencja: klucz jest zajmowany **przed** wykonaniem handlera w `gfm.idempotency` (PK `(org_id, principal_id, key)`), razem z `payload_sha256` = sha256(`METODA ŚCIEŻKA\n` + ciało). Ten sam klucz i ten sam payload → zapamiętana odpowiedź bajt w bajt z `Idempotent-Replay: true`. Ten sam klucz i inny payload → `409 idempotency_payload_mismatch`. Klucz zajęty przez trwające żądanie → `409 idempotency_in_progress`. Nieudana mutacja zwalnia klucz, więc porażka nigdy nie jest odtwarzana jako sukces.
- **Odpowiedź „na żywo".** Trasy `POST {org_base}/repos`, `POST {repo_base}/imports`, `.../finalize` i `.../cancel` zajmują klucz tak samo (równoległy duplikat dostaje `409 idempotency_in_progress`, inny payload `409 idempotency_payload_mismatch`), ale powtórzenie z tym samym payloadem **wykonuje handler ponownie** i odpowiada `Idempotent-Replay: false`. Ich ciało jest widokiem bieżącego stanu: odtworzenie pierwszej odpowiedzi `POST …/imports` kazałoby wznowionej synchronizacji wysłać bloby, które serwer już ma — czyli dokładnie ten przypadek, dla którego klucz istnieje (U1.4). Gwarancja „bez podwójnej pracy" pochodzi tam z samego zasobu: jeden import na `manifest_digest`, jeden job na `idempotency_key`. Trasy, których odpowiedź jest zapisem faktu (`.../feedback` → `judgment_id`), odtwarzają ciało jak dotąd.
- Idempotencja nie zamraża autoryzacji: uprawnienia są sprawdzane ponownie przy każdym odtworzeniu.

`kinds` na `GET …/plan` jest listą wartości `{extraction|enrichment|consolidation}` zakodowaną jako pojedynczy parametr zapytania rozdzielony przecinkami (np. `?kinds=extraction,enrichment`), zgodnie z ogólną regułą jednowartościowych parametrów zapytania (§3); nieobecny lub pusty `kinds` znaczy „wszystkie trzy rodzaje". `POST …/proposals:generate` przyjmuje `kinds` jako tablicę JSON w ciele (ciało nie ma tego ograniczenia) i zakłada po jednym jobie `proposal.generate` na każdy żądany rodzaj (§8), więc `job_ids` w odpowiedzi może nieść kilka pozycji. `plan` w odpowiedzi generowania ma ten sam kształt `ImportPlan` co `GET …/plan` (§5.2) i odzwierciedla limity faktycznie zastosowane do tego wywołania, nie tylko oszacowanie sprzed startu. Rodzaj propozycji `scope_map` (§4.4, 1.15.0) **nie jest** dopuszczalną wartością `kinds` na żadnej z tych dwóch tras: powstaje z własnego rodzaju joba `scope_map.propose` (§8), a nie z `proposal.generate`, więc `kinds=scope_map` to `400 invalid_request`.

`profile` (parametr zapytania na `GET …/plan`, pole ciała na `POST …/proposals:generate`) należy do zamkniętego zbioru `{default|one_shot}`; nieznana wartość to `400 invalid_request`, a brak pola znaczy `default`. `one_shot` podnosi **wyłącznie** `max_groups` do liczby grup, które plan rzeczywiście znalazł (twardy sufit 1000 grup na rodzaj), tak aby jedno wywołanie objęło cały import i `groups_skipped` było zerowe. Żaden inny limit się nie zmienia: `max_usd`, `max_calls`, `max_tokens`, `max_neighbours`, `max_files` i `max_bytes` pozostają ceilingiem wdrożenia, a wywołujący nadal może je obniżyć w `limits` — zawężenie działa po zastosowaniu profilu, więc `one_shot` nigdy nie przywraca limitu, który wywołujący celowo obniżył. Odpowiedź obu tras niesie `profile` z nazwą profilu, który faktycznie wykonano, a `limits.max_groups` po planowaniu jest liczbą grup do uruchomienia, nie sufitem — właściciel widzi koszt przed startem także wtedy, gdy startuje wszystko naraz (U2.7).

**`POST {repo_base}/github/import` i `POST {org_base}/github/import` (1.13.0, Task 3).** Importowanie repozytorium zarejestrowanego z połączonej instalacji GitHub (§4.7) bez uploadu manifestu i bez klucza modelu organizacji: obie trasy kolejkują job `github.import_repo` (§8), który powtarza wyłącznie pierwsze dwa etapy `live.repo` — fetch i `import.parse` — nigdy `proposal.generate`. Klucz modelu organizacji zostaje wyłącznie wymaganiem propozycji (duplikaty, sprzeczności), nie samego importu. `{repo_base}/github/import` odrzuca repozytorium bez `github_installation_id` (`repo_not_github_linked`, 404) — zarejestrowane ręcznie albo przez CLI, nie przez `github.sync_repositories`. `{org_base}/github/import` kolejkuje po jednym jobie dla każdego repozytorium organizacji, które ma `github_installation_id`, jednym wywołaniem („Import all" nigdy nie jest pętlą klienta po repozytoriach) — `items` niesie `job_id` każdego z nich, puste, gdy organizacja nie ma jeszcze żadnego repozytorium zarejestrowanego z GitHuba. Repozytorium bez `guidefold.yaml` **jest importowane** (1.14.0, [ADR-0050](adr/ADR-0050-zero-config-scope-map.md)): mapa scope'ów zostaje wywnioskowana z katalogów skilli i CODEOWNERS, a `gfm.scopes.source` = `inferred`. Pomijane jest wyłącznie repozytorium, które **ma** `guidefold.yaml` nieczytelny dla tego przebiegu: job kończy się `worker.Skipped` z powodem `guidefold_yaml_unreadable`, zapisanym w `gfm.repos.import_blocked_reason` (§5.2, §7) — `Repo.import_blocked_reason` w odpowiedzi `GET {org_base}/repos` pokazuje to wprost, nigdy jako `failed`.

**Propozycja mapy organizacji `scope_map` (1.15.0, [ADR-0051](adr/ADR-0051-llm-proposed-organisation-map.md)).** Rodzaj `scope_map` opisuje strukturę **organizacji**, nie jednego pliku: jego węzły przypisują ścieżki wielu repozytoriów do wspólnej hierarchii. Wiersz nadal leży w `gfm.proposals` z `repo_id` repozytorium, którego import go wywołał (zakotwiczenie, nie zakres), a jego treść wymienia każde repozytorium jawnie. Dlatego decyzja ma własną trasę `POST {org_base}/proposals/{proposal_id}/decision`, jedyną mutację w `{org_base}`, i **wymaga ownera organizacji**. To nie jest wygoda, tylko poprawność uprawnienia: `repo_id` w wierszu jest repozytorium, którego import wywołał propozycję, a wiersze `gfm.scopes`, które zatwierdzenie zapisze, sięgają także pozostałych repozytoriów organizacji. Przyjęcie tej decyzji jako recenzenta repozytorium zakotwiczającego pozwoliłoby recenzentowi najmniejszego repozytorium przestawić scope'y wszystkich. Dlatego bliźniak `{repo_base}` **odmawia** decyzji na propozycji `scope_map` (`403 forbidden` z komunikatem wskazującym trasę organizacji) — inaczej byłby obejściem tej kontroli. Dla pozostałych rodzajów trasa `{org_base}` stosuje dokładnie tę samą regułę recenzenta co `{repo_base}`, na repozytorium z wiersza propozycji, a `{repo_base}` działa bez żadnej zmiany.

Trzy zachowania są dla `scope_map` inne niż dla trzech rodzajów generowanych kandydatów:

- `decision: approve` **stosuje** mapę — zapisuje wiersze `gfm.scopes` z `source='llm_approved'`, `reviewed_by` i `proposal_id` — i przenosi propozycję do stanu `applied` (§6). Nie powstaje rewizja skilla, bo `scope_map` nie proponuje żadnego `SKILL.md`.
- `decision: edit` kończy się `invalid_candidate_change`: kandydatem jest tu typowany JSON mapy, a nie ciało karty, więc „poprawię ręcznie" nie ma dziedziny, w której mogłoby być poprawne. Właściciel, który chce innej mapy, odrzuca propozycję i zapisuje `guidefold.yaml` — plik z ADR-0050 ma pierwszeństwo nad każdą propozycją.
- `POST …/export` na propozycji `scope_map` to `proposal_state_invalid`: nie ma pliku ani patcha do wydania.

Mapa, która nie przechodzi walidacji z §5.4 (cykl rodzica, ścieżka w dwóch węzłach jednego repozytorium, nazwa spoza ADR-0008, rodzic spoza mapy), daje `422 scope_map_invalid` z `details.findings[]` i **nie zmienia niczego**. Walidacja biegnie przy zapisie propozycji w workerze i ponownie przy zatwierdzeniu, bo między jednym a drugim mógł dojść import, który zmienił ścieżki.

**Publikacja importu `partial` (1.17.0).** Import w stanie `partial` **publikuje się**. U2.1 mówi, że jeden zepsuty plik ma upaść sam, a reszta importu ma zostać przyjęta; odmowa całego snapshotu łamała drugą połowę tego zdania — repozytorium z jedną niepoprawną kartą nie mogło opublikować żadnej z pozostałych. `publish.build` buduje więc snapshot z plików zaakceptowanych i:

- zapisuje `gfm.publications.partial = true`, a `Snapshot` (§5.4) niesie `partial:bool!` i `failed_files:[]obj!` — po jednym wpisie `{path, reason}` na plik, którego ten import nie sparsował (wprost z `gfm.import_files`, gdzie `import.parse` zapisał `errors[]` z inwentarza buildera). `ImportPublication` (§5.2) niesie `partial:bool?` w tej samej roli. Konsola pokazuje tę adnotację przy imporcie i przy snapshocie: publikacja niekompletna, która nie mówi o sobie, że jest niekompletna, byłaby gorsza niż odmowa;
- kończy się `failed` z `error: import_partial` **wyłącznie**, gdy import `partial` nie ma ani jednego pliku nadającego się do publikacji. Wtedy nie ma z czego zbudować snapshotu i kod zostaje przy dotychczasowym znaczeniu „ten import nie da snapshotu";
- każdy nieudany plik dostaje jedną pozycję kolejki właściciela `import_file_failed` (§5.5), pisaną przez `import.parse` w tej samej transakcji co drift. Pozycja nie znika sama — zamyka ją wyłącznie decyzja właściciela (U9), tak jak przy `source_changed`. Kolejny import, który plik sparsuje, nie rozstrzyga jej za niego.

Nic z tego nie rusza bramki zaufanej publikacji: snapshot dalej buduje zaufany builder z obrazu workera, walidacja grafu dalej biegnie przed ruchem head, a nieudana walidacja dalej zostawia poprzedni snapshot serwujący.

Rozszerzenie 1.2 (`schema_version: "1.2"`): żądanie przyjmuje dodatkowe pole najwyższego poziomu `search_snapshot:str?` (walidowane osobnym dokumentem `tools/serve_spike/contracts/harness-service-v1.2.schema.json`, nadzbiorem 1.1; w żądaniu 1.1 to pole jest nieznane i daje `400`). USE zwraca `closure: {status: complete|unresolved|cannot_fit, requires: [{skill_id, revision, status, depth}], depth_limit: 8, loaded: [...]}` respektując `budget.max_cards` (domyślnie 4, maksimum 4 jak w 1.1) i `loaded_skills`; `status` zależności to `loaded|available|denied|missing`, a `depth` liczy skoki od żądanego skilla. USE zwraca też `resources: [{path, sha256, size, required, url}]` — manifest plików pakietu tej rewizji, z `path` **względnym wobec katalogu pakietu** i `url` wskazującym `GET /v1/skills/{skill_id}/revisions/{revision}/resources/{path}`; wymagany zasób bez bajtów daje `409 missing_required_resource`, a `resources: []` oznacza, że snapshot nie ma manifestu dla tej rewizji, nie że pakiet jest pusty. Podanie `search_snapshot` różnego od aktywnego daje `409 snapshot_changed` i ponowny SEARCH; nigdy mieszanki rewizji. Klient 1.1 nie otrzymuje żadnej z tych gwarancji przez samą zmianę etykiety.

Tryb `proof_gated` jest addytywnym, jawnym opt-in w żądaniu USE 1.2 (`delivery_policy:"proof_gated"`). W tym trybie serwer zwraca `delivery:{action:LOAD|ASK,reason,missing[],provenance}`. `LOAD` zostaje wydany tylko wtedy, gdy opublikowana karta niesie ważny, źródłowo związany dowód: identyfikator skilla, rewizja, snapshot, hash body, wszystkie rozwiązane scope'y, kompletna closure oraz każdy obowiązkowy claim ma status `supported` i niepusty zakres linii źródłowych. Przed wydaniem `LOAD` Go sprawdza, że każda ścieżka claimu należy do manifestu aktywnej rewizji albo wskazuje opublikowany skill/document z tego samego repozytorium i snapshotu, a następnie pobiera wskazany content-addressed blob z `gfm.blobs` (dla `SKILL.md` używa dokładnie dostarczanego body), sprawdza jego SHA-256 i obecność deklarowanego zakresu linii. Przy braku dowodu, konflikcie, niezgodności rewizji/snapshotu/scope'u, niepełnej closure, niedostępnym lub zmienionym źródle albo nieprawidłowym zakresie linii odpowiedź ma `action:"ASK"`, `status:"ask"`, `body:""` i opisuje brakujące warunki; pusty body nie jest instrukcją do wstrzyknięcia. `provenance` pokazuje wyłącznie identyfikatory, hashe i zakresy linii, nigdy treść źródła. Domyślny tryb (`legacy` lub brak pola) zachowuje dotychczasową odpowiedź 1.2. To jest bramka źródłowego pochodzenia i spójności dostawy, nie dowód poprawności wykonania ani autoryzacji człowieka.

W snapshotach rekord wejściowy nosi nazwę `source_proof` i znajduje się na
poziomie frontmatteru `SKILL.md`, poza skalarnym `metadata`; builder przenosi go
do pola karty `proof`. Wymagany kształt wersji `source-proof-v1` odpowiada
projekcji `delivery.provenance`: `schema`, `verified`, `snapshot`, `skill_id`,
`revision`, `body_sha256`, `scopes`, `claims[]` oraz opcjonalne `conflicts[]`.
Claim może dodatkowo nieść `claim_refs[]`: content-addressed pointers
(`skill_id`, `revision`, `claim_id`, `claim_digest`, `commitment`) do wspierających
claimów niższej karty w tym samym snapshotcie. Przy takim dowodzie serwis
przechodzi rekurencyjnie po całej ścieżce; brak karty, zmiana commitmentu/digestu,
konflikt lub cykl daje `ASK`.
`verified:true` jest oświadczeniem zaufanego importera/reviewera po sprawdzeniu
źródła i zakresów linii, a nie wartością, którą klient może nadać w żądaniu.
Brak tego rekordu jest celowo bezpieczny: tryb proof-gated zwraca `ASK`.
Publisher wiąże jawne placeholdery `pending`/puste dla `snapshot`, `revision` i
`body_sha256` z aktywnym snapshotem, rewizją karty i dostarczanymi bajtami. Nie
podnosi `verified` i nie nadpisuje wartości podanej przez reviewera; błędna wartość
pozostaje błędem, który kończy się `ASK`.
Rewizja karty obejmuje body i metadane retrieval, ale wyłącza wyłącznie kopertę
`proof`, aby jej publisher-bound pola nie tworzyły cyklicznego hasha.

1.2 dodaje też `family` — po jednym obiekcie na każdą kartę `cards[]` i `ranked[]` w SEARCH oraz jeden na odpowiedź USE: `family: {parent: {skill_id, revision, layer} | null, children: [{skill_id, revision, scope, layer}], layer}`. Wyliczane jest z zatwierdzonych krawędzi `refines` (dziecko → rodzic) i z `gfm.skills.knowledge_layer`; `layer` należy do `{atomic|task|abstract}` albo jest `null`, gdy nikt jeszcze nie sklasyfikował skilla. Głębokość to **jeden skok**, `children` ma najwyżej 8 pozycji w kolejności `skill_id`, a krawędź wskazująca poza snapshot nie jest więzią rodzinną i nie pojawia się w ogóle. `family` jest wskazówką nawigacyjną, nigdy deklaracją kompletności: nie mówi, że lista dzieci jest pełna, i nie zastępuje `closure`, które odpowiada na inne pytanie („czego jeszcze potrzebuję, żeby to uruchomić"). **`family` nie ma znaczenia rankingowego.** Jest doklejane po rankingu, po selekcji i po zmierzeniu `card_context`, więc kolejność `ranked`/`cards` oraz każdy bajt rozliczenia budżetu są identyczne z nim i bez niego; żądanie 1.1 nie dostaje tego pola w ogóle. Jeżeli metadane piramidy miałyby kiedykolwiek wpływać na retrieval, wymaga to osobnej, ograniczonej i z góry opisanej ewaluacji (PIVOT-BACKLOG, „Zasady prowadzenia", P06–P08).

**Jawne połączenie (ADR-0034), nie zgadywanie po slugu.** Wcześniejsza wersja tej sekcji mapowała konto/organizację GitHub na organizację Guidefold, jeśli ich identyfikatory akurat się zgadzały — działało to tylko wtedy, gdy slug Guidefold przypadkiem równał się loginowi GitHub, więc dla Aplikacji instalowanej przez kogokolwiek (jak Codecov) instalacja spoza tego jednego przypadku ginęła po cichu z `organization_not_found`. To dopasowanie zostało **usunięte całkowicie**, bez zachowania jako fallback — fallback byłby tą samą dziurą. Instalację łączy z organizacją wyłącznie `gfm.github_installation_links`, zapisywane jedynie przez poniższy `callback` po **udowodnionym** połączeniu, nigdy przez webhook.

**Start.** Właściciel klika w konsoli Guidefold (nie wkleja URL-a GitHuba); `start` tworzy jednorazowy podpisany `state` w `gfm.auth_states` (te same `newAuthState`/`matchAuthStateCookie`/`consumeAuthState` co logowanie, rodzaj `github_install`, z `org_id` przywiązanym do wywołującej organizacji — kolumna `org_id` na `gfm.auth_states` istnieje właśnie po to) i zwraca `install_url = https://github.com/apps/<GITHUB_APP_SLUG>/installations/new?state=<state>`. Na tym ekranie GitHuba właściciel wybiera „All repositories” albo wybrane repozytoria — Guidefold nie może tego wybrać za niego — a konsola **rekomenduje „All repositories”**, żeby każde przyszłe repozytorium trafiało do Guidefold bez ponownego przechodzenia przez ten przepływ. `GITHUB_APP_SLUG` nigdy nie jest zaszyty na sztywno.

**`return_to` (1.13.0, Task 1).** Znaleziono, że każdy przycisk „Connect GitHub" na kreatorze organizacji i na ekranie importu (`ui/src/routes/OnboardingRoutes.tsx` ~806/810) w rzeczywistości wołał `signIn('github')` — zwykłe logowanie tożsamościowe przez WorkOS, które nigdy nie instaluje Aplikacji GitHub Guidefold ani nie łączy niczego z tą trasą. Jedyne poprawne wywołanie, `startGitHubInstall`, żyło dotąd wyłącznie w zakładce Organization › Integrations, a `callback` zawsze wracał na `/organization?tab=integrations`, więc nawet po naprawie przycisku właściciel kreatora ląduje w innym miejscu, niż zaczął. `start` przyjmuje teraz opcjonalne `return_to` w ciele — jeśli obecne, walidowane przez `sanitizeGitHubReturnTo` (`identity/github_link.go`) przeciw zamkniętej liście ścieżek konsoli (`githubInstallReturnPaths`: dziś `/import`, `/organization`) po `url.Parse`: pusty `Scheme`/`Host` (nigdy pełny URL, nigdy schemat) i `u.Path` dokładnie na liście. Cel spoza listy albo niepoprawny jest **ignorowany**, nie odrzucany — żądanie po prostu spada na dotychczasowy domyślny cel (Integrations), tak jakby `return_to` nie było wysłane; ciało pozostaje opcjonalne, więc dzisiejszy przycisk zakładki Integrations, który nic nie wysyła, działa bez zmian (`c.Decode` jest wołane tylko, gdy ciało nie jest puste — `POST` bez ciała nadal odpowiada `200`, nigdy `invalid_body`). Zwalidowana wartość jest zapisywana w tym samym wierszu `gfm.auth_states.return_to`, który już istniał (kolumna `NOT NULL`, dotąd zawsze wypełniana samym `consoleReturn(org.ID, "")`); `callback` odczytuje ją z powrotem (`finishReturn`, ten sam plik) i dokleja `?github=<kod>` przez `url.Values`, nigdy przez sklejanie stringów — `org` z zapytania oryginalnego `return_to` (jeśli kreator albo ekran importu je tam już wpisał) nigdy nie jest nadpisywane. Brak zaufanego `return_to` w chwili odmowy (ciasteczko niedopasowane, stan już zużyty) spada na dotychczasowy `consoleReturn`, dokładnie jak przed 1.13.0.

**Callback.** GitHub przekierowuje z powrotem z `code`, `installation_id` i tym samym `state` („Request user authorization (OAuth) during installation”). `installation_id` w query stringu jest sterowany przez atakującego i sam w sobie nic nie dowodzi — dlatego callback wymienia `code` na token użytkownika (`POST https://github.com/login/oauth/access_token`, `GITHUB_APP_CLIENT_ID` + `GITHUB_APP_CLIENT_SECRET_FILE`), woła tym tokenem `GET /user/installations` i łączy `installation_id` z organizacją **tylko** wtedy, gdy ta lista go zawiera; w przeciwnym razie `installation_not_owned` i nic nie zostaje połączone. Obie rozmowy z GitHubem żyją w `internal/ghapp` (jedynym pakiecie, który rozmawia z `github.com`/`api.github.com`), nie w handlerze webhooka. `state` jest zdejmowany przez `consumeAuthState` (jednorazowy, z `expires_at`) i dodatkowo zestawiany z ciasteczkiem `gf_auth_state` dokładnie tak, jak `handleCallback` logowania — więc powtórzony albo cudzej przeglądarki `state` kończy się `invalid_state`, zanim callback zdąży cokolwiek połączyć.

**Ten endpoint jest celem nawigacji przeglądarki, nie wywołaniem JSON API — więc nigdy nie renderuje koperty błędów `mgmt.Router` (1.8.0 naprawia defekt, w którym każda odmowa odpowiadała gołym JSON-em: `mgmt.Fail`/`mgmt.Invalid` trafiały prosto do `render`).** Każda gałąź, sukces i każda odmowa jednakowo, kończy się przekierowaniem na `return_to` tego przebiegu (`finishReturn`, `identity/github_link.go`) z dopisanym `?github=<kod>` — jednym budowniczym adresu, żadne wywołanie nie dokleja parametru do cudzego URL-a ręcznie. Brak zaufanego `return_to` (nie wysłano go przy `start`, albo odmowa nastąpiła zanim jakikolwiek stan został odczytany — ciasteczko niedopasowane) spada na `consoleReturn`, dotychczasowy domyślny cel `/organization?tab=integrations[&org=<org_id>]` sprzed 1.13.0. `org_id`, nie slug, gdziekolwiek ten domyślny budowniczy go dokłada: `ui/src/app.tsx`'owy parametr `org` przyjmuje jedno i drugie identycznie (dopasowuje po `slug` albo `org_id` do własnych organizacji wywołującego), więc nie trzeba osobnego zapytania zamieniającego identyfikator na slug, a przekierowanie nigdy nie może wskazać organizacji, której ta przeglądarka nie udowodniła. `org` jest obecny w tym domyślnym celu tylko wtedy, gdy w chwili odmowy organizacja jest już udowodniona dla tej przeglądarki: brakuje go dla `invalid_callback`, `github_app_not_configured` i dla `invalid_state` z niedopasowanego ciasteczka albo już zużytego stanu — nigdy nie jest odczytywany z niesprawdzonego wejścia. Stan wygasły (`expired_state`) **niesie** organizację i `return_to`: ciasteczko już dowiodło, że ta przeglądarka zaczęła dokładnie ten przebieg, więc `consumeAuthState` odczytuje `org_id`/`user_id`/`return_to` zaraz po `DELETE ... RETURNING`, zanim jeszcze sprawdzi `expires_at` — zaufanie do przekierowania, nigdy do samego łączenia. Błąd, którego kod `*mgmt.Error` nie nazywa (albo dowolna awaria bazy), ląduje jako `internal_error`, z przyczyną zalogowaną po stronie serwera zamiast pokazaną przeglądarce — dokładnie to, co `mgmt.Router.render` robiłby przed napisaniem koperty, której ten handler już nigdy nie osiąga.

`handleCallback` logowania WorkOS (`/api/v1/auth/callback`) i `GET /api/v1/invitations/{token}/accept` (`handleInvitationLanding`) są tym samym rodzajem punktu: cele nawigacji przeglądarki, nie JSON API. Obie miały ten sam defekt i obie są naprawione w 1.8.0 tą samą zasadą — nigdy JSON, zawsze przekierowanie z zamkniętym kodem: logowanie na `/login?auth=<kod>` (`invalid_callback`, `invalid_state`, `expired_state`, `provider_unavailable`, `internal_error`; strona logowania pokazuje jedną linię z wynikiem), zaproszenie z niepoprawnym (pustym albo dłuższym niż 256 znaków) tokenem na `/invitations/invalid/accept` — token tej długości nigdy nie mógł nazywać prawdziwego zaproszenia (`gfm.invitations.token_sha256` to skrót stałej długości krótkiego sekretu), a konsola na tym adresie zgłasza „invitation not valid" dokładnie tak samo, jak dla poprawnie zbudowanego tokenu, który `POST .../accept` później odrzuci (ten przycisk nigdy nie odpala się sam przy wejściu na stronę).

**Kolejność zdarzeń.** Zdarzenie `installation` `created` może dotrzeć, zanim właściciel skończy `callback` (albo odwrotnie). Webhook zawsze utrzymuje wiersz-lustro `gfm.github_installations` (klucz to samo `installation_id`, bez `org_id` — instalacja istnieje niezależnie od tego, czy ktokolwiek ją połączył) niezależnie od tego, czy istnieje połączenie; `callback` zawsze zapisuje `gfm.github_installation_links` niezależnie od tego, czy wiersz-lustro już istnieje (tworzy pusty, jeśli nie). Obie kolejności zbiegają się więc do tego samego stanu: jedno połączenie, z listą repozytoriów odświeżoną przez `github.sync_repositories` (patrz §8) — ten job kolejkuje `callback` po połączeniu i webhook po każdym `installation`/`installation_repositories`, które dotyczy już połączonej instalacji; dla instalacji bez połączenia webhook nie kolejkuje niczego. `installation` `deleted` odłącza (nigdy nie kasuje) zreconciled repozytoria tej organizacji i usuwa wiersz-lustro, co kasuje też jego wiersz w `gfm.github_installation_links` (klucz obcy `ON DELETE CASCADE`). `DELETE {org_base}/github/installations/{id}` odłącza organizację od instalacji (usuwa tylko wiersz linku i odłącza jej repozytoria) — instalacja może dalej istnieć po stronie GitHuba.

**Brak trasy ręcznego ponowienia reconciliation (1.9.0, uwaga zakresu, nie wdrożenie).** Dziś nic poza tymi dwoma zdarzeniami webhooka i tym `callback` nie kolejkuje `github.sync_repositories`; nie ma `POST {org_base}/github/installations/{id}:resync` ani żadnej innej trasy, którą właściciel mógłby sam odpalić. Dla `installation_not_found`/`permission_refused` to nie jest luka — naprawa (ponowne połączenie, albo zatwierdzenie uprawnień na GitHubie) i tak sama z siebie generuje nowe zdarzenie webhooka, które ponownie kolejkuje job. Dla wyczerpanego `provider_unavailable` po przejściowej awarii GitHuba właściciel dziś rzeczywiście czeka na kolejne `installation`/`installation_repositories` zamiast móc spróbować od razu — warta osobnej decyzji właściciela, nie zbudowana w tej zmianie.

Webhook nie czyta ciała skilli i nie wywołuje modelu ani GitHuba: weryfikuje podpis, dla `pull_request` (`opened`, `synchronize`, `reopened`) sprawdza, czy `installation.id` jest połączone (`gfm.github_installation_links`) i czy `repository.full_name` należy do tej instalacji oraz do `gfm.repos` tej organizacji, po czym kolejkuje **jeden** job `pr.report` (klucz idempotencji `pr:<installation_id>:<pr_number>:<head_sha>`) — dla **każdego** PR, nie tylko takiego, który ruszył plik skilla. Ładunek `pull_request` nie niesie listy zmienionych plików, więc rozstrzyganie tego w handlerze wymagałoby wywołania GitHuba, którego handler robić nie może; listę pobiera worker tokenem instalacji i to on kolejkuje `ascend.run`, gdy są wśród niej pliki skilli (ADR-0036 pkt 1). Zdarzenie bez połączonej instalacji lub bez dopasowanego repozytorium odpowiada `202 {accepted:false, reason:"unknown_installation"}` — GitHub nie ma dostać `4xx` za instalację, której ta organizacja nie połączyła (albo za ładunek bez `installation.id`/`repository.full_name`/numeru PR-a/`head.sha`, który i tak nie dałby się dopasować). Token instalacji (JWT z `GITHUB_APP_PRIVATE_KEY_FILE` → `POST /app/installations/{id}/access_tokens`) jest pobierany przez **workera** per job, ważny godzinę, nigdy zapisywany w bazie ani logach.

### 4.8 Klucze modelu organizacji (ADR-0045 — BYOK)

| Metoda | Ścieżka | Rola / zakres | Wejście | Wyjście | Błędy | Idem. | P / AC |
|---|---|---|---|---|---|---|---|
| GET | `{org_base}/credentials` | member | — | `{items: [OrgCredential]}` | — | nie | ADR-0045 |
| PUT | `{org_base}/credentials/{provider}` | owner + CSRF | `{api_key:str!, name:str?, model:str?, preferred:bool?}` | `OrgCredential` | `invalid_provider`, `invalid_model`, `invalid_body`, `credential_invalid`, `provider_unavailable`, `secret_encryption_unavailable` | nie (nadpisanie jest z natury idempotentne) | ADR-0045 |
| PATCH | `{org_base}/credentials/{provider}` | owner + CSRF | `{model:str?, preferred:bool?}` | `OrgCredential` | `invalid_provider`, `invalid_model`, `invalid_body`, `credential_not_found` | nie | ADR-0045 |
| DELETE | `{org_base}/credentials/{provider}` | owner + CSRF | — | `204` | `credential_not_found` | nie | ADR-0045 |

Klucz nigdy nie wraca z API. `GET` i odpowiedź `PUT` niosą wyłącznie `provider`, `name`, `last4`, `model`, `preferred`, `created_at` i `created_by`. `PUT` przed zapisem sprawdza klucz u dostawcy jednym tanim wywołaniem i odrzuca taki, którego dostawca nie akceptuje — przyjęcie klucza, który nie działa, przeniosłoby awarię do joba w tle, którego właściciel nie ogląda. Zapis, nadpisanie, usunięcie i **użycie** klucza zapisują wiersz `gfm.audit` (`credential.set`, `credential.delete`, `credential.used`), zawsze z `last4`, nigdy z czymś więcej.

`PATCH` istnieje po to, żeby zmiana modelu albo przeniesienie znacznika `preferred` nie wymagały ponownego podania klucza. Formularz, który każe wkleić sekret, żeby przestawić jedno pole wyboru, uczy ludzi wklejania sekretów — a klucza i tak nie da się pokazać z powrotem, więc „potwierdź kluczem" nie jest tu żadnym potwierdzeniem. `PATCH` nie przyjmuje `api_key`; podmiana klucza to `PUT`, który jak dotąd weryfikuje go u dostawcy.

Dostawca i model są **ustawieniem organizacji, nie polem uruchomienia**. Pierwszy zapisany klucz staje się `preferred`; kolejny nie odbiera tego poprzedniemu, dopóki właściciel nie poprosi wprost (`preferred:true`, co zdejmuje znacznik z pozostałych). Praca, która używa klucza organizacji — dziś Live Agent, jutro każdy inny przebieg — bierze klucz oznaczony `preferred` i zapisany przy nim `model`; nie pyta o to przy starcie, bo wybór modelu jest decyzją organizacji podejmowaną raz, a nie pytaniem zadawanym człowiekowi, który chce tylko odświeżyć bibliotekę. `model` pominięty to domyślny model tego dostawcy. `model` **nie ma zamkniętej listy**: sprawdzany jest tylko kształt identyfikatora (bez spacji, do 120 znaków), bo katalog modeli należy do dostawcy, zmienia się co tydzień i lista trzymana tutaj odmówiłaby organizacji jej własnego dostrojonego modelu. Czy model istnieje, odpowiada dostawca, a przebieg kończy się wtedy `model_not_available`.

### 4.9 Live Agent (ADR-0046 — odświeżenie biblioteki po podpiętych repozytoriach)

| Metoda | Ścieżka | Rola / zakres | Wejście | Wyjście | Błędy | Idem. | P / AC |
|---|---|---|---|---|---|---|---|
| POST | `{org_base}/live/runs` | owner + CSRF | `{}` | `202` `LiveRun` | `model_credential_missing`, `live_run_already_active`, `secret_encryption_unavailable` | tak | ADR-0046 / U4 |
| GET | `{org_base}/live/runs` | member | `limit`, `cursor` | `{items: [LiveRun], next_cursor}` | `invalid_cursor` | nie | ADR-0046 / U4 |
| GET | `{org_base}/live/runs/{run_id}` | member | — | `{run: LiveRun, targets: [LiveRunTarget]}` | `live_run_not_found` | nie | ADR-0046 / U4 |
| GET | `{org_base}/live/runs/{run_id}/events` | member | `after:int?`, `limit` | `{items: [LiveRunEvent], next_after:int!, done:bool!}` | `live_run_not_found`, `invalid_integer` | nie | ADR-0046 / U4 |
| POST | `{org_base}/live/runs/{run_id}/cancel` | owner + CSRF | — | `LiveRun` | `live_run_not_found`, `live_run_not_cancellable` | nie | ADR-0046 / U4 |

`…/events` jest jedynym kanałem żywego wyjścia i **nie** jest transportem strumieniowym: zwykła koperta z §3, kursor pozycyjny `after` zamiast nieprzezroczystego `next_cursor`, bo dziennik jest monotoniczny w `seq` i klient dopytuje o „co po tym, co już mam". `next_after` to `seq` ostatniego zwróconego zdarzenia (albo `after`, gdy nic nie doszło), a `done` jest prawdziwe dopiero wtedy, gdy przebieg się zakończył **i** zwrócono już ostatnie zdarzenie — klient przestaje odpytywać wyłącznie na `done`, nigdy na pustej stronie. Dziennik jest też zapisem przebiegu: druga osoba i odświeżona karta widzą dokładnie to, co pierwszy oglądający widział na żywo.

**Żądanie startu nie ma pól.** To jest cała treść decyzji właściciela: jeden przycisk, nie formularz. Nie ma promptu, bo zadanie jest zawsze to samo i należy do produktu, a nie do człowieka, który ma je za produkt wymyślić; nie ma wyboru repozytoriów, bo przebieg z definicji obejmuje wszystkie podpięte; nie ma wyboru dostawcy ani modelu, bo to ustawienie organizacji z §4.8. Pole, którego nie ma w żądaniu, nie może też zostać źle wypełnione — dlatego trzy błędy walidacji wejścia z poprzedniej wersji tej sekcji zniknęły, a nie przeniosły się.

Przebieg robi dokładnie to, co robi istniejący przepływ importu i propozycji, tylko sam i po wszystkim naraz: czyta `AGENTS.md` i pliki `SKILL.md` każdego podpiętego repozytorium przez aplikację GitHub, przepuszcza je przez `import.parse`, **odświeża katalog** i uruchamia `proposal.generate` rodzaju `consolidation`, który porównuje parami skille scope'u nadrzędnego i jego dzieci i z tego powstają **duplikaty i sprzeczności jako propozycje w istniejącym przeglądzie**. Po przebiegu zostaje biblioteka i lista propozycji do decyzji, a nie transkrypt do przeczytania i wyrzucenia.

Organizacja bez zapisanego klucza dostaje `model_credential_missing` **przy starcie**, a nie w tle: to jedyny warunek, który da się sprawdzić przed zakolejkowaniem czegokolwiek, więc sprawdzamy go tam, gdzie człowiek patrzy. Wyczerpany limit u dostawcy widać dopiero przy wywołaniu i kończy przebieg jako `partial` z `model_quota_exhausted`.

Repozytorium bez instalacji aplikacji GitHub dostaje własny wiersz `LiveRunTarget` w stanie `skipped` z `github_app_not_configured` — przebieg „po wszystkich repozytoriach", który po cichu pominął część, byłby gorszy od takiego, który się nie udał.

### 4.10 Zakres organizacji dla odczytów (1.11.0)

Decyzja właściciela, 2026-09-13: **domyślnym zakresem odczytu konsoli jest organizacja**, a repozytorium jest filtrem, nie warunkiem wstępnym ([ADR-0047](adr/ADR-0047-organisation-is-the-default-read-scope.md)). Każdy odczyt `GET {repo_base}/…` wymieniony w §4.2–§4.6 z dopiskiem „(§4.10)" ma bliźniaka `GET {org_base}/…` o tym samym kształcie odpowiedzi i tych samych parametrach plus opcjonalne `repo`. Trasy `{repo_base}` zostają bez zmian; mutacje (decyzja, eksport, feedback, publikacja, kolejka, import) pozostają wyłącznie per repozytorium, a klient bierze `repo_id` z wiersza, na którym działa.

1. **Zakres.** Odpowiedź `{org_base}` obejmuje **repozytoria dostępne dla principala**: owner — wszystkie `gfm.repos` organizacji; member — te bez ACL (`gfm.repo_acl_policies`/`gfm.repo_members` puste) oraz te z jawnym grantem w `gfm.repo_members`. To ta sama reguła, którą `{repo_base}` stosuje do jednego repozytorium, więc widok organizacji nigdy nie pokazuje wiersza, którego ten sam member nie mógłby przeczytać per repozytorium. Organizacja bez dostępnego repozytorium odpowiada pustą listą, nie błędem.
2. **`repo`.** Zawęża odczyt do jednego repozytorium i wtedy odpowiedź jest **identyczna** z `{repo_base}` dla tego repozytorium. Nieznane `repo` → `not_found`; znane, ale bez dostępu → `forbidden`; niepoprawny format → `invalid_repo_id`.
3. **`repo_id` na wierszu.** `SkillSummary`, `ProposalSummary`, `ImportStatus`, `QueueItem`, `MapScopes.scopes[]` i `MapScopes.unmapped[]` niosą `repo_id:str!`; `UsageSkill` niesie `repo_id:str?` (`null` dla skilla, którego katalog nie zna). Koperta listy (`org_id`, `repo_id`) ma `repo_id: null`, gdy odpowiedź obejmuje więcej niż jedno repozytorium, i identyfikator, gdy została zawężona. Pola są addytywne i obecne także w odpowiedziach `{repo_base}`.
4. **Facety.** `field=repo` liczy skille per repozytorium (`value` = `repo_id`). `FilterEcho` dla `repo` w `SkillPage.filters` jest echem parametru jak dla pozostałych pól.
5. **Drzewo źródeł.** `GET {org_base}/map/repository` bez `repo`: pusty `path` zwraca po jednym dziecku na dostępne repozytorium (`kind: repository`, `name` = `path` = `repo_id`, `count` = liczba skilli i dokumentów), a `path` zaczyna się od `<repo_id>/` i dalej jest ścieżką w tym repozytorium; ścieżki dzieci również niosą ten przedrostek. `MapChild.kind` przyjmuje `repository` obok `dir|skill|document`.
6. **Scope w wielu repozytoriach.** Identyfikator scope'u jest unikalny w repozytorium (`gfm.scopes PK(org_id,repo_id,scope)`), nie w organizacji. `GET {org_base}/map/scopes?scope=` i `GET {org_base}/modules/{scope}` bez `repo` odpowiadają dla scope'u obecnego w dokładnie jednym dostępnym repozytorium; obecnego w kilku → `scope_ambiguous` (409) z komunikatem, że trzeba podać `repo`. Lista scope'ów bez `scope` zwraca węzły wszystkich dostępnych repozytoriów, każdy z `repo_id`.
7. **Usage.** Ledger jest już w skali organizacji (§4.6); `{org_base}/usage` liczy wiersze wszystkich dostępnych repozytoriów plus skille nieznane katalogowi (jak dotąd), `coverage` i `health` opisują organizację, `queue` łączy kolejki dostępnych repozytoriów, a `filters` dostaje echo `repo` tylko wtedy, gdy podano. `previous` liczone tak samo. Eksport zyskuje **ostatnią** kolumnę `repo_id` (addytywnie, §5.5).
8. **Live Agent** (§4.9) już działa na wszystkich podpiętych repozytoriach organizacji (1.6.0) i nie zmienia się w tej rewizji.
9. **Duplikaty między repozytoriami (1.12.0).** `GET {org_base}/skills/duplicates` zwraca grupy skilli o tej samej `name` w **co najmniej dwóch różnych dostępnych repozytoriach** (reguła dostępu z pkt 1; skille `source_status: removed` nie liczą się). Trasa istnieje tylko w zakresie organizacji, bez bliźniaka `{repo_base}`: duplikat między repozytoriami wymaga więcej niż jednego. Z `repo=X` zostają wyłącznie grupy zawierające X, ale członkowie grupy nadal pochodzą ze wszystkich dostępnych repozytoriów, bo duplikaty X leżą w innych. Porządek `count desc, name asc`; kursor keyset na `(count, name)`; `limit` 1–100, domyślnie 50. Równość nazw jest dokładna (z rozróżnieniem wielkości liter); wykrywanie podobieństwa jest poza zakresem i należy do propozycji rodzaju `consolidation` (§4.2). `identical:true` wtedy i tylko wtedy, gdy każdy członek ma niepuste i równe `content_sha256`.
10. **Jedna mutacja w zakresie organizacji (1.15.0).** Zdanie ze wstępu tej sekcji — „mutacje pozostają wyłącznie per repozytorium" — zyskuje jeden jawny wyjątek: `POST {org_base}/proposals/{proposal_id}/decision` (§4.4, [ADR-0051](adr/ADR-0051-llm-proposed-organisation-map.md)). Powód jest wąski i nie uogólnia się: decyzja na propozycji `scope_map` zapisuje wiersze `gfm.scopes` w **kilku** repozytoriach organizacji, więc uprawnienie musi być organizacyjne, a nie repozytoryjne. Trasa nie poszerza uprawnień w dół — przeciwnie, dla `scope_map` wymaga więcej (owner organizacji) niż bliźniak `{repo_base}` wymaga dla pozostałych rodzajów (recenzent repozytorium), a `{repo_base}` odmawia tej decyzji wprost, więc nie da się nią obejść kontroli. Dla pozostałych rodzajów trasa stosuje tę samą regułę recenzenta na repozytorium z wiersza propozycji. Pozostałe mutacje (eksport, feedback, publikacja, kolejka, import) **nie** dostają bliźniaka; wniosek o kolejny wymaga własnego wiersza w tym punkcie.

## 5. Schematy DTO

Notacja pól: `nazwa:typ!` wymagane i nie-null, `nazwa:typ?` może być `null` lub nieobecne, `{a|b|c}` dziedzina zamknięta. Typy: `str`, `int`, `num`, `bool`, `ts` (RFC 3339, UTC), `uuid`, `sha` (64 hex), `urn` (`urn:skill:<publisher>:<node>:<name>`), `obj`, `[]T`. Dekoder klienta ignoruje pola nadmiarowe i odrzuca brakujące zadeklarowane (`ui/src/api/decoders.ts`). Serwer odrzuca nieznane pola **żądania** (`400 invalid_json`).

porażka (`gfm.github_installation_links.last_sync_failed_at`/`last_sync_failure_reason`, pisane wyłącznie przez `github.sync_repositories`, §8) ustawia oba pola i **nie** zależy od tego, czy `synced` było kiedyś `true` — to, co konsola pokazuje, jest zawsze wynikiem ostatniego przebiegu, nie historią; kolejny sukces czyści oba pola w tej samej transakcji, w której ustawia `repositories_synced_at`, więc naprawiona reconciliation nigdy nie zostawia po sobie martwej porażki. `sync_failure_reason` nie ma zamkniętej dziedziny w notacji typu (nowe przyczyny mogą się pojawić bez migracji tego pola), ale dzisiejszy słownik to dokładnie cztery wartości, wyprowadzone z nazwanych błędów, które `internal/ghapp` już rozróżnia (`ghapp.ErrInstallationNotFound`, `ghapp.ErrPermissionRefused`), plus jeden osobny kod zapisywany przez `Run` wprost, nie wymyślone tutaj: `installation_not_found` (GitHub 404 — instalacja usunięta albo odinstalowana po stronie GitHuba **albo** zawieszona — `ghapp/errors.go`'owy komentarz przy `ErrInstallationNotFound` nazywa oba stany; konsola odróżnia je przez `suspended` z tego samego wiersza, bo działanie właściciela jest przeciwne dla każdego z nich: dla zawieszonej — wznowić instalację na GitHubie; dla usuniętej — rozłączyć (`DELETE .../installations/{id}`) i połączyć ponownie od zera; `provider_unavailable` (wszystko inne, czego `ghapp` nie nazwał — timeout, 5xx, nieczytelna odpowiedź; ten sam ogólny „GitHub nie odpowiedział", którego już używa przepływ callbacku w tej samej sekcji) — zapisywane dopiero, gdy `t.Job.Attempts >= t.Job.MaxAttempts` na tej próbie (ostatnia próba jest wyczerpaniem retry, nie każda porażka po drodze), działanie właściciela: poczekać na kolejne zdarzenie webhooka albo spróbować później — dziś nie ma trasy ręcznego ponowienia (patrz uwaga w §4.7 poniżej); Pusta komórka CSV odpowiada `null` w JSON — brak oceny nie jest zerem, więc `helped…feedback_n`, `helped_numerator`, `helped_denominator` i `small_sample` są puste, gdy dla wiersza nie ma żadnej oceny.

**Definicje miar (U6).** Liczone wyłącznie ze zdarzeń klienta; odpowiedź HTTP nie jest dowodem.

| Miara | Definicja |
|---|---|
| `exposures` | Unikalne `exposure_id` zdarzeń `card_injected` w oknie |
| `loads_verified` | Unikalne `load_id` zdarzeń `skill_load_completed` o `status ∈ {ok, verified}`; `denied`/`error` nigdy nie są załadowaniem |
| `context_loaded` | Te z nich, których `skill_load_completed` niesie `context_confirmation: "context_loaded"` (pole opcjonalne, addytywne) |
| `context_unknown` | `loads_verified − context_loaded`: `download_verified`, `unsupported` i brak pola to *unknown*, nie porażka |
| `exposures_expanded` | Ekspozycje (`card_injected`), których `search_id` występuje też na zweryfikowanym `skill_load_completed` **tego samego `skill_id`** w oknie. `skill_load_completed` niesie `search_id` jako pole **opcjonalne, addytywne** (jak `context_confirmation`; nie ma go na liście `required_fields` walidatora, adapter 1.1 działa dalej). Powiązanie jest po `skill_id`, nie po rewizji: karta i body tego samego skilla mogą nieść różne identyfikatory rewizji (rewizja karty vs katalogu), a pytanie brzmi „czy po tej karcie pobrano body", nie „którą rewizję" |
| `loads_unlinked` | Zweryfikowane załadowania bez `search_id` — adapter nie wiedział, po jakiej ekspozycji je wykonał. To *unknown*, nie „bez karty": dopóki `loads_unlinked > 0`, `exposures − exposures_expanded` jest górną granicą liczby kart, które wystarczyły |
| `use_reported` / `use_observed` | Osobno, deduplikowane po `use_id` (brak `use_id` → po `event_id`); nigdy nie sumowane |
| `use_episodes` | Unikalne `(tenant, task_id, skill_id, revision)` w obu rodzajach łącznie; zdarzenie bez `task_id` nie tworzy epizodu |
| `feedback` | Jedna opinia na epizod: korekta niesie `corrects_judgment_id` wskazujący wcześniejsze `judgment_id` i **zastępuje** je (kolejność po `occurred_at`, potem `event_id`), a nie dodaje drugiego głosu |
| `skill_feedback` z UI | `POST …/revisions/{revision_id}/feedback` zapisuje `revision` = rewizja katalogu (adresowana w ścieżce) plus **opcjonalne** `content_sha256` i — gdy rewizja weszła do snapshotu — `card_revision`. Oba pola są opcjonalne i nie występują na liście `required_fields` walidatora (`telemetry-schema.json` bez zmian), więc adapter 1.1 i klient 1.1.0 działają dalej. `revision` celowo zostaje przy rewizji katalogu: to jedyny z trzech identyfikatorów, który kontrolna implementacja `tools/telemetry/report.py` potrafi policzyć bez dostępu do katalogu |

| `zero_loads` | Brak zweryfikowanego załadowania w oknie; nie dowodzi bezużyteczności |
| `coverage.oldest_lag_s` | Największy `oldest_lag_s` z `gfm.adapter_health` organizacji; brak wiersza to `null` (nieznane), nie zero |

Kolejka (`Usage.queue`) łączy otwarte wiersze `gfm.owner_queue` (przyczyny driftu pisane przez workera importu) z dwiema przyczynami **policzonymi** z telemetrii: `negative_feedback` (≥1 `hindered` w oknie na bieżącej lub opublikowanej rewizji) i `zero_loads` (skill opublikowany, ≥1 ekspozycja **albo** ≥7 dni od publikacji, zero załadowań). Pozycja policzona ma stabilny identyfikator `<reason>:<skill_id>:<revision>` i również podlega decyzji: decyzja zapisuje wiersz `gfm.owner_queue` w stanie `resolved`, którego `item_id` jest deterministycznie wyprowadzone z tego identyfikatora, więc ta sama obserwacja nie wraca i nie dubluje się. Istniejący wiersz o tym samym `(skill_id, reason, revision_id)` — otwarty albo już rozstrzygnięty — wygasza pozycję policzoną.

Przyczyna **`import_file_failed`** (1.17.0) jest pisana przez workera `import.parse` w tej samej transakcji co drift: jedna pozycja na plik, którego builder nie sparsował, z `evidence` = `{import_id, path, error}`. Nie ma automatycznego zamknięcia — kolejny import, który plik sparsuje, nie kasuje pozycji ani jej nie rozstrzyga, bo „plik znów się parsuje" nie odpowiada na pytanie, czy wiedza z niego jest poprawna; zamyka ją wyłącznie decyzja właściciela, tak jak każdą inną pozycję (U9). Decyzja na tej pozycji nie rusza statusu publikacji żadnego skilla — nie ma skilla, którego mogłaby dotyczyć.

Decyzja ownera na pozycji **`source_changed`** zamyka też pytanie, które drift postawił skillowi: `POST {repo_base}/usage/queue/{item_id}/decision` z akcją `reviewed`, `fixed_in_git` albo `no_change` przenosi skill z `needs_review` z powrotem do `published` w tej samej transakcji, w której zapisuje decyzję (§6). Decyzja na pozycji **`source_removed`** niczego nie cofa: skill zostaje `archived`, bo pliku nadal nie ma w repozytorium, a przywraca go dopiero import, który go z powrotem przynosi. Żadna inna przyczyna nie rusza statusu publikacji.

Każde zdarzenie niesie `payload.text:str!` — jedno zdanie **w języku konsoli** (dziś angielskim, jak cała reszta interfejsu), gotowe do wypisania; konsola pokazuje dziennik, a nie tłumaczy kody na zdania po swojej stronie, bo wtedy druga osoba czytająca ten sam przebieg przez API widziałaby coś innego niż właściciel. `repo.fetched` niesie `{files:int!}`, `repo.parsed` `{skills:int!, import_id:uuid!}`, `repo.proposed` `{proposals:int!}`, `run.finished` `{counts:obj!, summary:obj!}`, `error` `{reason:str!}`. Nie ma zdarzenia niosącego surowy strumień modelu: model jest wołany wewnątrz `proposal.generate`, którego wynikiem jest propozycja do zatwierdzenia, a nie tekst do oglądania. Dziennik jest przez to ograniczony konstrukcyjnie — najwyżej kilka zdarzeń na repozytorium — ale sufit **20 000 zdarzeń** zostaje jako bezpiecznik: po jego osiągnięciu worker dopisuje jedno zdarzenie `error` z powodem `live_run_log_truncated` i dalej zapisuje wyłącznie `repo.finished` i `run.finished`. |

### 5.6 Manifesty i artefakty

`guidefold-import-manifest-v1` (produkowany lokalnie przez CLI, wysyłany w `POST {repo_base}/imports`):

| Pole | Typ | Semantyka |
|---|---|---|
| `format` | `"guidefold-import-manifest-v1"!` | Inna wartość → `400 unsupported_manifest_format` |
| `org`, `repo` | `str!` | Slug org i `repo_id` (`[A-Za-z0-9_.-]{1,64}`) |
| `commit` | `str?` | 40 hex albo `null` dla skanu bez gita |
| `complete` | `bool!` | `false` (skan częściowy) **nigdy** nie prowadzi do usunięć |
| `dirty` | `bool!` | Lokalne zmiany; domyślny profil publikacji obejmuje commit |
| `cli_version`, `scan_profile`, `root` | `str!` | Diagnostyka i zakres skanu |
| `files` | `[]obj!` | `path`, `sha256`, `size`, `kind:{skill\|document\|config\|resource}`, `mode`, `source:obj?` |
| `files[].source` | `obj?` | Nieobecne dla plików repozytorium (domyślne, wstecznie zgodne). Obecne wyłącznie dla treści spoza drzewa git, dołączonej jawnym `guidefold extract --personal`: `{kind:"personal", harness:{claude\|codex\|copilot}}`. Ścieżka takiego pliku ma prefiks `_personal/<harness>/…` i nigdy nie koliduje ze ścieżką repozytorium. Bez `--personal` żaden wiersz z `source.kind:"personal"` nie istnieje; CI nigdy nie używa tej flagi. Manifest zawierający choć jeden taki wiersz ma `publish:false` — kompletny import z `publish:true` zleca `publish.build`, więc prywatne skille dewelopera zaczęłyby odpowiadać na SEARCH całej organizacji z jednej flagi |
| `excluded` | `[]obj!` | `path`, `reason:{secret_pattern\|ignored_directory\|symlink_outside_root\|submodule\|unsupported_format\|limit_exceeded\|non_canonical_skill_path}` |
| `aliases` | `[]obj!` | `from`, `to` — zachowanie tożsamości przy rename (U1.5) |
| `limits` | `obj!` | `max_files`, `max_bytes` deklarowane przez klienta; serwer i tak stosuje własne |
| `publish` | `bool?` | Domyślnie `true`. `false` finalizuje import bez joba `publish.build`: drzewo jest sparsowane, katalog uzupełniony, ale nic nie startuje do publikacji (§6) |
| `suggestions` | `[]obj!` | Doradcze dopasowania scope/owner dla plików `kind:skill`, których `guidefold.yaml` samodzielnie nie pokrywa (U1 AC2): `path`, `suggested_scope:str?`, `suggested_owner:str?`, `reasons:[]str`, `candidates:[]str?` (przy `ambiguous_node_match`). Nigdy nie wpływa na `files`/`excluded` ani na scope faktycznie użyty przez CLI — czysto informacyjne, obecne (może być puste) w każdym manifeście |

Manifest jest deterministyczny: to samo drzewo daje identyczne bajty (porządek po bajtach ścieżki). `manifest_digest` = sha256 kanonicznego JSON-a manifestu.

`guidefold-service-snapshot-v1` — istniejący artefakt buildera snapshotu (wiąże `repo_id`, commit, mapę scope, karty, wagi i sha CLI). Kontrakt bez zmian; opis w [HARNESS-SERVICE-CONTRACT §Scope resolution](HARNESS-SERVICE-CONTRACT.md).
`router_index` — istniejący kanoniczny indeks leksykalny budowany przez zaufany Python builder; postać i digest bez zmian (`gf.router_indexes`, `gf.router_terms`). Ten kontrakt go **nie** redefiniuje.

## 6. Maszyny stanów

Każde przejście ma aktora, warunek i efekt uboczny. Efekt „audyt" oznacza wiersz w `gfm.audit` z `request_id`.

| Maszyna | Przejście | Kto | Warunek | Efekt uboczny |
|---|---|---|---|---|
| import | `created → uploading` | API | pierwszy `PUT …/blobs/{sha}` | licznik `new_blobs` |

| import | `queued → parsing` | worker | lease joba `import.parse` | `started_at`, heartbeat |
| import | `parsing → ready` | worker | wszystkie pliki `accepted` | rewizje, dokumenty, zasoby, drift; audyt |
| import | `parsing → partial` | worker | ≥1 plik `failed`, reszta `accepted` | jak wyżej; publikacja **nie** startuje samoczynnie |
| import | `parsing → failed` | worker | manifest lub bloby nieczytelne | brak zmian w katalogu; aktywny snapshot bez zmian |
| import | `* → cancelled` | owner (API) | `cancel` | joby `queued → cancelled`, job `leased` kończy na najbliższym checkpoincie |
| publikacja | `none → building` | API/worker | `publish.build` zaleasowany | `gfm.publications` |
| publikacja | `building → validated` | worker | graf i pakiety poprawne | `validation.ok = true` |
| publikacja | `validated → active` | worker | transakcja zapisu `gf.snapshots/skills/heads` | zmiana `gf.heads`; audyt |
| publikacja | `building\|validated → failed` | worker | walidacja lub transakcja nieudana | poprzedni head bez zmian; `error` |
| publikacja | `active → superseded` | worker/owner | aktywacja innego snapshotu (rollback lub roll-forward) | audyt; retencja ≥30 dni |
| job | `queued → leased` | worker | `lease_until < now()` lub `state='queued'` | `generation += 1`, `worker_id`, `attempts += 1` |
| job | `leased → leased` | worker | heartbeat ≤10 s, generacja zgodna | `lease_until` przedłużony, `checkpoint` |
| job | `leased → done` | worker | handler zwrócił `nil` | `result`, `finished_at` |
| job | `leased → failed` | worker | błąd trwały lub `attempts ≥ max_attempts` | `error`; backoff 5 s, 10 s, 20 s… ≤5 min |
| job | `leased → queued` | worker | błąd przejściowy, `attempts < max_attempts` | `lease_until` = teraz + backoff |
| job | `leased → skipped` | worker | brak pracy (np. `llm_not_configured`) | `error` = powód; import pozostaje użyteczny |

| proposal `scope_map` | `draft → rejected` | owner organizacji (`{org_base}`) | `decision: reject` z powodem | `cache_key` zablokowany: ta sama mapa z tej samej recepty nie wraca |
| skill | `draft → approved_for_export → awaiting_git → published` | jak wyżej | — | draft nigdy nie trafia do SEARCH/USE |
| skill | `published → needs_review` | worker (drift) | inny sha źródła albo negatywny feedback | pozycja `owner_queue`; poprzedni snapshot działa dalej |
| skill | `* → archived` | worker (drift) | brak w **kompletnym** manifeście (`source_removed`) | nigdy nie usuwamy wiersza; decyzja należy do ownera |

| device code | `approved → (skonsumowany)` | API | pierwsza udana wymiana | token osobisty; kod jednorazowy |
| membership | `(brak) → member\|owner` | owner (zaproszenie) / API (twórca org) | akceptacja zaproszenia w terminie | audyt |
| membership | `owner → member`, `* → (brak)` | owner | nie jest to ostatni owner | audyt; dostęp odcięty przy następnym żądaniu |
| invitation | `pending → accepted\|revoked\|expired` | zapraszany / owner / czas | token jednorazowy | audyt |

`applied` jest stanem **końcowym** i należy wyłącznie do rodzaju `scope_map` (1.15.0): propozycja mapy nigdy nie przechodzi przez `approved_for_export`, `awaiting_git` ani `published`, bo nie ma pliku, który miałby trafić do gita. Odwrotnie też: żaden z trzech rodzajów generowanych kandydatów nie osiąga `applied`. Zatwierdzenie mapy **dopisuje i zmienia** wiersze `gfm.scopes`, nigdy nie kasuje: scope, którego mapa nie wymienia, zostaje taki, jaki był, bo cichy zanik węzła zabrałby skille z widoku bez decyzji człowieka. Pierwszeństwo źródeł rozstrzyga [ADR-0050](adr/ADR-0050-zero-config-scope-map.md) — `guidefold.yaml` przed zatwierdzoną propozycją, zatwierdzona propozycja przed mapą wywnioskowaną — więc późniejszy import z `guidefold.yaml` nadpisuje wiersz `llm_approved`, a nie odwrotnie.

Ten sam cykl publikacji widziany przez import ma tylko cztery wartości: `ImportPublication.state` (§5.2) zwija `building`/`validated` do `building` i `active`/`superseded` do `published`, bo z perspektywy importu liczy się, czy publikacja **kiedykolwiek** osiągnęła `active`, nie czy nadal jest bieżącym snapshotem.

## 7. Schemat bazy

Dwa schematy, jedna baza (ADR-0018, ADR-0033). `gf` to istniejący katalog serwowania: **niezmienny poza dopisaniem kolumn**, zgodnie z profilem plain Postgres (`pg_search` i `pgvector` są opcjonalne; migracja musi przejść bez nich, a silnik `router` nigdy ich nie czyta). `gfm` to schemat zarządczy: każdy wiersz danych organizacyjnych ma `org_id`, a każdy klucz złożony zaczyna się od `org_id`, więc zapytanie bez predykatu tenanta nie może połączyć organizacji.

Rola `guidefold_api` ma `default_transaction_read_only=on`; każdy zapis otwiera jawną transakcję read-write. `gf.*` pozostaje dla API tylko do odczytu z wyjątkiem append do `gf.events` i `gf.search_shadow`; wiersze katalogu pisze wyłącznie job publikacji.

Liczniki `produced`/`acknowledged`/`dropped` sumują to, co adapter zaraportował w `telemetry_health`; `oldest_lag_s` **zastępuje** poprzednią wartość, bo to stan bieżący, a adapter, który nadrobił zaległości, nie może dalej wyglądać na spóźniony. Feedback z UI **nie** ma własnej tabeli: `POST …/feedback` zapisuje zdarzenie `skill_feedback` do `gf.events` z `tenant_id = org_id` i zwraca `judgment_id`, żeby jedna definicja oceny obsługiwała adapter i UI.

**Retencja blobów** jest ręcznie wywoływaną komendą operatora, `guidefold-search blobs-retain [days] [now]` (na wzór istniejącego `telemetry-retain`), **nie** rodzajem (`kind`) joba z §8 — nic w kolejce `gfm.jobs` jej nie leasuje. „Referencowany" sha256 to taki, który występuje w `gfm.skill_revisions`, `gfm.skill_resources` lub `gfm.documents` nie-zarchiwizowanego skilla, albo należy do importu młodszego niż `days` (domyślnie 30, jak w kolumnie Retencja `gfm.blobs`). Nie-referencowany blob starszy niż `days` jest usuwany; wiersze, które go opisywały (import, skill, rewizja), nie są ruszane.

**Dlaczego bloby i telemetria są w Postgres w MVP.** Jedna baza oznacza jedną transakcję dla enqueue joba razem z wierszami, które go uzasadniają, jeden model uprawnień i jedno miejsce retencji; wolumen pilota (100 MiB na import, 200 skilli) mieści się bez obiektowego magazynu, a GCS dodałby drugą granicę autoryzacji i drugi tor awarii przed pierwszym klientem (ADR-0033). Port wyjściowy jest już zdefiniowany: `BlobStore` z operacjami `Put(org, sha, bytes)`, `Get(org, sha)`, `Stat`, `Delete` — adapter Postgres dziś, adapter GCS (obiekty pod `<bucket>/<org_id>/<sha256>`, dostęp krótkożyjącymi referencjami) później, bez zmiany domeny. Migracja polega na przepisaniu zawartości i przełączeniu adaptera; ten kontrakt się wtedy nie zmienia, bo `gfm.blobs.content` jest jedyną kolumną, którą traci.

## 8. Kontrakt API–worker

Job jest jedynym kanałem między API a workerem. Enqueue odbywa się w transakcji wywołującego (`jobs.Queue.Enqueue(ctx, tx, job)`), więc job nigdy nie istnieje bez wierszy, które go uzasadniają.

| Pole joba | Źródło | Reguła |
|---|---|---|
| `schema_version` | API | W `payload`; worker odrzuca nieznaną wersję zamiast zgadywać |
| `org_id`, `repo_id`, `import_id` | API | Worker sprawdza tożsamość org i aktualne uprawnienie **przed** pracą |
| `kind` | API | Z zamkniętej listy poniżej |
| `input_digest` | API | `manifest_digest` albo sha256 posortowanych sha wejść; podstawa dedupe |
| `recipe_version` / `model_revision` | API | Część klucza cache generowania |
| `idempotency_key` | API | UNIQUE `(org_id, idempotency_key)`; ponowne enqueue zwraca istniejący job |
| `limits` | API | `max_files, max_bytes, max_tokens, max_groups (5), max_proposals_per_group (5), max_neighbours (10), max_calls, max_usd` |
| `generation` | queue | Rośnie przy każdym lease; każdy zapis workera niesie swoją generację |
| `checkpoint` | worker | Pozwala wznowić bez duplikowania kandydatów (dedupe po `input_digest`) |
| `cost` | worker | `JobCost`; `usd_uncertain` dla opłat po timeoucie |

Lease: `UPDATE gfm.jobs SET state='leased', generation=generation+1, … WHERE state='queued' OR (state='leased' AND lease_until < now())`. Lease trwa 30 s, heartbeat co najwyżej 10 s. Zapis z nieaktualną generacją nie zmienia nic i zwraca `job_fenced` (`jobs.ErrFenced`); heartbeat, który zobaczy fencing, anuluje kontekst handlera, więc spóźniony worker przestaje pisać. Backoff 5 s, 10 s, 20 s… do 5 minut, `max_attempts` domyślnie 3.

Próba, która jeszcze ma retry w zapasie, nie zapisuje niczego — link ma dalej czytać jako „jeszcze nie uruchomione", nie jako „nieudane", dopóki naprawdę nie ma już nic do spróbowania. **Ten sam zapis dzieje się też, bezwarunkowo, gdy `w.gh` jest `nil`** (worker'a własna połowa App-a nieskonfigurowana — `github_app_not_configured`), tuż przed `worker.Skipped`: `worker.Skipped` jest tak samo ostateczne jak `worker.Permanent` (`internal/worker`'owe `finish` nigdy nie ponawia skipu), więc bez tego zapisu ta gałąź zostawiałaby dokładnie tę samą lukę, którą ta cała zmiana zamyka — tylko osiągniętą inną drogą niż błąd GitHuba. | brak (jedna reconciliation na job) | brak wywołania modelu |

Repozytorium bez `guidefold.yaml` jest importowane z mapą `inferred` (1.14.0, ADR-0050); `worker.Skipped` z `guidefold_yaml_unreadable` i zapis `gfm.repos.import_blocked_reason` (§5.2, §7) zamiast `gfm.imports` dotyczy wyłącznie zadeklarowanego pliku, którego nie da się odczytać; sukces czyści tę kolumnę z powrotem do `NULL`. | `import_id` i `job_id` joba `import.parse`, na który czeka | `max_files` (domyślne `Limits`); bez wywołań modelu |

Sufity przebiegu nie są dziś polem żądania: `live.plan` zapisuje do `gfm.live_runs.limits` wartości domyślne **2,00 USD**, **50 000 tokenów wejścia na repozytorium** i **200 plików na repozytorium**. Właściciel ich nie podaje, bo pierwsza wersja ma mieć jeden przewidywalny koszt, a nie regulator, którym da się go przypadkiem podnieść; gdy pojawi się pole żądania, domyślne zostają te same.

Repozytorium jest wiązane z instalacją aplikacji GitHub przez `gfm.repos.git_host_url` dopasowany do `full_name` w `gfm.github_installations.repositories` (`live.plan`) albo przez `gfm.repos.github_installation_id` zapisane bezpośrednio przez `github.sync_repositories` (§4.7/powyżej, `pr.report`). Odkąd `github.sync_repositories` sam rejestruje repozytoria organizacji z listy instalacji, `git_host_url` dla repozytorium zarządzanego instalacją jest pisany przez Guidefold, a nie wpisywany ręcznie — ale samo dopasowanie w `live.plan` wciąż jest porównaniem stringów wyprowadzonego URL-a, a nie kluczem obcym, i `GitHubInstallation.repositories[].repo_id` z §5.1 wciąż jest zawsze `null`. To więc **węższe** obejście niż przed jawnym połączeniem, nie rozwiązanie: pełne domknięcie wymagałoby, żeby `live.plan` też czytał `gfm.repos.github_installation_id` zamiast wyprowadzać URL. Repozytorium bez rozpoznawalnego adresu hosta wciąż dostaje cel `skipped` z `github_app_not_configured` — nazwany, nie pominięty.

`live.repo` **nie woła modelu sam**. Pobiera `AGENTS.md` i pliki `SKILL.md` przez adapter aplikacji GitHub, przepuszcza je przez wewnętrzny szew importera (te same operacje `CreateImport`/`PutBlob`/`FinalizeImport`, które obsługuje HTTP, wołane w tej samej transakcji bez pośrednictwa HTTP), kolejkuje `import.parse`, a po nim `proposal.generate` rodzaju `consolidation`. Wykrywanie duplikatów i sprzeczności to ten drugi job i nic tu go nie duplikuje: własne wołanie modelu obok istniejącego generatora byłoby jego gorszą kopią, która na dodatek nie zostawia po sobie propozycji.

Z tego wynika jedna rzecz, którą trzeba było rozstrzygnąć: **`live.repo` czeka na joby, które sam zakolejkował.** Jeden job prowadzi jedno repozytorium od pobrania do propozycji, odpytując wiersz joba potomnego i dopisując zdarzenie na każdym przejściu. Alternatywa — żeby to `import.parse` i `proposal.generate` zgłaszały się z powrotem — wymagałaby, by oba wiedziały o przebiegu Live Agenta, o którym nie mają prawa wiedzieć i który istnieje bez nich. Oczywisty zarzut wobec czekania to długo trzymana dzierżawa; odpowiedź jest w kolejce: dzierżawa trwa 30 s i jest przedłużana `Heartbeat` co najwyżej co 10 s, a `Heartbeat` z nieaktualną generacją zwraca `ErrFenced`, więc job, który przespał swoją dzierżawę, dowiaduje się o tym i kończy, zamiast pisać obok przejętego przez kogoś innego. Anulowanie przebiegu jest widziane na tym samym odpytywaniu, a nie dopiero po repozytorium.

Cel repozytorium przechodzi w stan końcowy wyłącznie w `live.repo`, bo tylko ten job wie, że etap `propose` się domknął. Dzięki temu `maybeFinishRun` po każdym domknięciu celu zostaje tym, czym jest — przebieg kończy się wtedy i tylko wtedy, gdy nie ma już celu w stanie `queued` ani `running`.

`live.plan` i `live.repo` (ADR-0046) **czytają** repozytorium przez API treści GitHuba tokenem instalacji — wyłącznie `guidefold.yaml`, `AGENTS.md`, `CODEOWNERS`, `.github/CODEOWNERS`, `docs/CODEOWNERS` (1.17.0) i `**/.agents/skills/**/SKILL.md`. `guidefold.yaml` jest na tej liście, bo to on **nazywa** hierarchię scope'ów, gdy repozytorium chce ją nazwać po swojemu. Od 1.14.0 ([ADR-0050](adr/ADR-0050-zero-config-scope-map.md)) jego brak nie blokuje importu: `import.parse` buduje hierarchię wywnioskowaną z katalogów skilli, a `gfm.scopes.source` = `inferred`; owner takiego węzła bierze się z CODEOWNERS, i **dlatego** trzy kanoniczne ścieżki CODEOWNERS (kolejność wyszukiwania `_CODEOWNERS_CANDIDATES` z CLI) są na liście pobierania od 1.17.0 — bez nich ta droga importu dawała `owner: unknown`, a propozycje `scope_map` `owner: null`, choć repozytorium własność deklaruje. Pliki CODEOWNERS są w manifeście importu rodzajem `config` (nie `document`), więc nie stają się wiedzą w Bibliotece, i **nie mają pierwszeństwa** `guidefold.yaml` wobec `max_files`: mieszczą się w tym samym budżecie co karty, pod tym samym `MaxFileBytes`. Cel `skipped` z `guidefold_yaml_unreadable` dostaje wyłącznie repozytorium, które plik **ma**, a ten przebieg nie potrafi go odczytać — mapy zadeklarowanej przez właściciela nie zastępujemy zgadywaną. Nie klonują, nie uruchamiają niczego z repozytorium, nie zakładają gałęzi ani PR-a; to, co agent proponuje zmienić, idzie do istniejącego przepływu propozycji i czeka tam na decyzję człowieka. Klucz modelu należy do organizacji (ADR-0045): `proposal.generate` uruchomiony przez przebieg bierze klucz preferowanego dostawcy tej organizacji zamiast klucza wdrożenia, otwiera go w pamięci na czas jednego joba i nigdy nie wpisuje do `payload`, `checkpoint`, `result`, logu ani komunikatu błędu. Wyczerpanie `max_usd` albo `max_tokens` kończy przebieg jako `partial` z `live_run_budget_exhausted`, po zapisaniu wszystkich dotychczasowych zdarzeń. Anulowanie zatrzymuje `live.repo` na najbliższym checkpoincie, a nie na końcu repozytorium. Polityka sieciowa workera musi mieć wyjście do endpointu OpenRoutera obok GitHuba; do czasu tej zmiany job kończy się `skipped` z `github_app_not_configured`.

`ascend.run` (ADR-0036) wykonuje w workerze dokładnie to, co `guidefold ascend` w CI klienta (ADR-0035): klonuje `head_sha` tokenem instalacji do `/work`, uruchamia zaufany plik CLI z obrazu workera (`skills/guidefold/scripts/guidefold ascend --since <base_ref>`), a zapisane pliki wypycha na gałąź i otwiera PR, którego recenzentami są CODEOWNERS katalogów rodzica. Nigdy nie wykonuje skryptów z klonowanego repozytorium. Klucz modelu z `GUIDEFOLD_ASCEND_API_KEY_FILE`, klucz aplikacji z `GITHUB_APP_PRIVATE_KEY_FILE`, sekret webhooka z `GITHUB_WEBHOOK_SECRET_FILE` — wzorzec `*_FILE` jak u generatora. Obraz workera musi mieć `git`, a polityka sieciowa workera wyjście do `api.github.com`, `github.com` i endpointu modelu — dziś ma tylko DNS i bazę (deploy/k8s/chart/templates/worker.yaml), więc do czasu tej zmiany job kończy się `skipped` z `github_app_not_configured`.

Jest jeden rodzaj joba dla wszystkich propozycji, `proposal.generate`; rozróżnia je wyłącznie `payload.kind`. `POST {repo_base}/imports/{import_id}/proposals:generate` przyjmuje tablicę `kinds` i zakłada po jednym jobie na każdy żądany rodzaj, więc odpowiedź `{job_ids, plan}` może nieść kilka `job_id`. Nie ma osobnego `kind` joba `consolidate`.

Dla `payload.kind = consolidation` wejściem jest zbiór skilli **scope'u nadrzędnego i jego bezpośrednich dzieci**, a nie jednego scope'u: skille scope'u trafiają do grupy scope'u, który je zawiera, a skille scope'u najwyższego poziomu do grupy `_root`. Każdy skill należy do dokładnie jednej grupy — wspólny element zaproponowany pod dwoma różnymi przodkami byłby dwiema propozycjami z dwoma kluczami cache dla jednej wiedzy. Wewnątrz grupy porównywane są wszystkie pary, bo wspólny element widoczny dopiero w trzecim i piątym runbooku jest właśnie tym, którego człowiek ręcznie nie znajdzie; `max_neighbours` ogranicza zarówno wkład jednego scope'u, jak i liczbę scope'ów wnoszących do grupy, więc grupa ma najwyżej `max_neighbours²` skilli (100 przy domyślnych) i liczba porównań jest kwadratowa w małej stałej, **nigdy** w rozmiarze repozytorium. Limit nie jest nakładany na sklejoną listę: obcięcie sklejenia pozwoliłoby pierwszemu scope'owi w kolejności nazw wydać cały budżet i zostawić rodzeństwo bez porównania — czyli zgubić dokładnie te pary, dla których konsolidacja istnieje, i pary, które wcześniejsze grupowanie po pojedynczym scope już porównywało. To nadal nie jest przebieg all-pairs po katalogu.

Wspólny element trafia do scope'u będącego najgłębszym wspólnym przodkiem swoich źródeł (`_root`, gdy nie mają innego), niesie `derived_from` do każdego źródła i proponuje `refines` z każdego źródła w górę do siebie (§5.4). Podniesienie scope wymaga ≥2 różnych scope'ów źródłowych i ownera scope'u docelowego jako ownera propozycji; inaczej zatwierdzenie kończy się `422 scope_widening_not_approved`. Każda odrzucona para ma jawny powód w `result.abstentions[]` (`no_shared_procedure`, `too_few_procedures`, `version_mismatch`, `condition_mismatch`, `contradictory_steps`, `already_consolidated`, `max_proposals_reached`); milczące pominięcie pary jest błędem.

`payload.profile` jest tym, co wybrał wywołujący na `…/proposals:generate` (§4.2). Wpływa wyłącznie na `limits.max_groups` zapisane w wierszu joba; worker czyta limity z wiersza, nie z profilu. Checkpoint jest **na grupę**: `{groups_done, cost, abstentions}` po każdej ukończonej grupie, więc przerwany przebieg one-shot wznawia się od następnej grupy, a grupy już zrobione nie tworzą nic nowego, bo klucz cache je odrzuca.

`publish.build` materializuje drzewo importu z blobów do prywatnego katalogu pod `.guidefold/worker/`, uruchamia **zaufany** builder `tools/worker/build_tree.py` (używa `load_map`/`Index.build`/`with_router_index` z CLI; sha CLI jest sha polityki), waliduje graf i dopiero wtedy zapisuje katalog w jednej transakcji. Do snapshotu wchodzą wyłącznie skille o statusie kwalifikującym do publikacji; nieudana walidacja zostawia poprzedni head. Import `partial` buduje się z plików zaakceptowanych i publikuje z `partial:true` (§4.4); `import_partial` zostaje wyłącznie na przypadek, w którym po odjęciu nieudanych plików nie zostaje nic do opublikowania. Obraz API **nie zawiera Pythona**; builder jest narzędziem obrazu workera. Worker nigdy nie wykonuje skryptów z importowanych pakietów.

**`scope_map.propose` (1.15.0, [ADR-0051](adr/ADR-0051-llm-proposed-organisation-map.md)).** Job jest kolejkowany przez workera `import.parse` po **udanym** imporcie (`ready` albo `partial`), w osobnej transakcji po tej, która zapisała katalog — import, który się nie udał, nie ma czego mapować. Kolejkowanie jest warunkowe: organizacja musi mieć klucz modelu (`gfm.org_credentials`, sprawdzane jak w `internal/live` — wyłącznie „czy jest", nigdy otwierane w API) **albo** wdrożenie musi mieć generator `deterministic`. Organizacja bez klucza przy generatorze `none` nie dostaje joba wcale, a job, który mimo to wystartuje i zobaczy `ErrNotConfigured`, kończy się `worker.Skipped("llm_not_configured")` — tak samo jak `proposal.generate` (U2.7: repozytorium importuje się bez klucza modelu, #146, #167).

Co job pokazuje modelowi jest zamkniętą listą i wynika z reguły trybu treści z [ADR-0041](adr/ADR-0041-training-signal-storage-and-dataset-boundaries.md): dla każdego repozytorium organizacji — jego `repo_id`, lista katalogów zawierających `SKILL.md`, istniejące węzły `gfm.scopes` (nazwa, rodzic, owner, ścieżki), reguły CODEOWNERS zaimportowane jako dokument, `guidefold.yaml`, jeśli repozytorium je ma, oraz **pierwsze 400 znaków** `README.md` i `AGENTS.md` korzenia. Nigdy cały kod, nigdy ciało `SKILL.md`, nigdy plik spoza tej listy. Wejściem jest struktura, bo pytanie brzmi „jak te katalogi układają się w organizację", a nie „co jest w tych plikach". **CODEOWNERS jest pobierany od 1.17.0.** Lista plików adaptera aplikacji GitHub obejmuje odtąd `CODEOWNERS`, `.github/CODEOWNERS` i `docs/CODEOWNERS` (§8), więc repozytorium zaimportowane tą drogą ma regułę własności w drzewie i propozycja może nazwać ownera. Repozytorium, które CODEOWNERS nie ma — albo którego CODEOWNERS nie mówi nic o danym katalogu — nadal daje `owner: null`, nigdy zgadniętą nazwę zespołu.

Model zwraca typowany JSON (`ScopeMap` z §5.4) i nic poza nim. Worker waliduje go **przed** zapisem: każda nazwa węzła jest poprawną ścieżką węzła — segmenty kebab-case `[a-z0-9][a-z0-9-]*` rozdzielone kropkami ([CONVENTIONS](CONVENTIONS.md) §1, „Nodes are dotted paths"), żaden segment nie zawiera `--`, bo to separator identyfikatora rejestru w [ADR-0008](adr/ADR-0008-skill-identity-resource-id-not-urn.md) decyzja 1 i segment z `--` przestałby być odwracalny, albo dokładnie `_root`, `parent` wskazujący inny węzeł tej samej mapy, graf rodzica acykliczny, każda ścieżka przypisana do dokładnie jednego węzła w obrębie swojego repozytorium (`(repo_id, path)`, bo identyfikator scope'u jest unikalny w repozytorium — §4.10 pkt 6), owner, za którego repozytorium ręczy — nazwa z jego CODEOWNERS albo owner, którego jego własne wiersze `gfm.scopes` już deklarują (`guidefold.yaml` jest wyższą instancją, więc nazwa z pliku nie jest zmyślona) — albo `null`. Mapa, która nie przechodzi, **nie tworzy propozycji**: job kończy się `worker.Permanent` z listą powodów w `result.findings[]`, bo ponowienie tego samego wywołania nie naprawi struktury, której model nie umiał zbudować. Klucz cache liczy się jak dla `proposal.generate` — `sha256(org, posortowane wejścia, recipe_version, model_revision, "scope_map")` — więc dwa importy pod rząd bez zmiany struktury nie dają drugiej propozycji, a mapa raz odrzucona nie wraca.

Generator: `GUIDEFOLD_GENERATOR=none|deterministic|openai|anthropic|openrouter`. `openrouter` mówi identycznym, kompatybilnym z OpenAI protokołem sieciowym (ten sam kształt żądania/odpowiedzi, ten sam nagłówek Bearer) — różni się od `openai` wyłącznie punktem końcowym i domyślnym modelem (`openai/gpt-4o-mini`, nadpisywalnym per organizacja w `gfm.org_credentials.model`), nie osobną implementacją. `none` kończy job jako `skipped` z `llm_not_configured` — import istniejących skilli pozostaje użyteczny (U2.7). `deterministic` (recepta `det-1`) obsługuje testy i demo offline. Każdy job `proposal.generate` najpierw sprawdza preferowany klucz organizacji (`internal/secrets.OpenPreferred`, §4.8/§5.5a); jeśli istnieje, generator jest budowany dla dostawcy i modelu tej organizacji — także wtedy, gdy różnią się od `GUIDEFOLD_GENERATOR` wdrożenia — i dopiero brak preferowanego klucza cofa job do generatora wdrożenia i jego `*_API_KEY_FILE`. Dostawcy HTTP używają `*_API_KEY_FILE` (albo klucza organizacji, otwieranego w pamięci na czas jednego joba i nigdy niezapisywanego do payloadu/checkpointu/wyniku/logu), timeoutów i ≤2 retry dla niepoprawnego JSON-a. Klucz cache = sha256(org, posortowane sha wejść, `recipe_version`, `model_revision`); `recipe_version` niesie nazwę dostawcy, więc dwie organizacje na różnych dostawcach nigdy nie dzielą klucza cache, a propozycja odrzucona z tym samym kluczem nie jest generowana ponownie.

## 10. Wersjonowanie

`contract_version` opisuje ten dokument i management API; `schema_version` w odpowiedzi opisuje ładunek: `mgmt-1` dla `/api/v1`, `1.1` i `1.2` dla `/v1`.

| Rodzaj zmiany | Wersja | Wymagania |
|---|---|---|
| Nowe pole odpowiedzi, nowy endpoint, nowy kod błędu, nowa kolumna nullable | `contract_version` PATCH/MINOR, `schema_version` bez zmian | Wpis w §11, aktualizacja OpenAPI, test odrzucenia nieznanego pola żądania |
| Zmiana znaczenia pola, usunięcie pola, zawężenie dziedziny, nowy wymagany parametr | `contract_version` MAJOR i nowe `schema_version` (`mgmt-2`, `1.3`) | Negocjowana wersja, równoległe wsparcie starej, ADR |
| Nowa gwarancja dostawy (closure, budżety, zasoby) | `1.2` i wyżej | Pełny zestaw testów z §9; 1.1 nie zmienia zachowania |

Serwer odrzuca nieznane pola żądania i nieznane wersje (`400`); klient toleruje addytywne pola odpowiedzi. `GET /health/ready` ogłasza wspierane wersje w `api_schema_versions`.

Wsparcie klienta CLI: jedna wersja `contract_version` MAJOR wstecz przez co najmniej 90 dni od wydania następnej. `guidefold doctor` zgłasza niezgodność wersji jako ostrzeżenie z konkretną komendą aktualizacji, a nie cichy fallback. Adapter, który nie potrafi obsłużyć zadeklarowanej wersji, **nie** ponawia żądania przez ciche usunięcie kontekstu workspace.
