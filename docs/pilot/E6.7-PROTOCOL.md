## 0. Why this is frozen before the first task runs

Every retrieval metric measured so far — Hit@1, `all_required@4`, HSR@4, latency — is a proxy.
None of them says whether serving skills changes what a developer actually does. E6.7 is the one
measurement that asks that question directly, by running matched tasks with and without the
system and comparing outcomes. A pilot whose tasks, conditions, outcome rule or analysis are
decided *after* seeing results is not evidence of anything except what the analyst wanted to see
— DENSE-PROGRAM.md §4a exists for exactly this reason on the retrieval side ("the honest handling
has to be written down before it becomes convenient"). This document is that same discipline
applied to task outcomes: the task bank, the conditions, the primary outcome rule, and the
analysis code are all fixed and hashed (§13) before task 1 begins. Amendments after freezing are
new dated addenda, appended below the frozen text, never edits to it — the same convention
DENSE-PROGRAM.md uses for its own versions.

## 1. Hypotheses

**H1 (primary).** For a named pairwise contrast, paired gain rate minus paired regression rate is
> 0, with a 95% interval on that difference excluding 0. Quoting
[SEARCH-USE-TELEMETRY.md §6](../SEARCH-USE-TELEMETRY.md), KPI 3, verbatim, as the definition this
protocol uses without modification:

> **Controlled task utility**: decide whether serving skills improves work. | Paired evaluated
> scenario: gain rate = baseline failure → selected-skill success / all paired evaluable
> scenarios; regression rate reverses the transition. | Pin inputs, model, harness and evaluator;
> compare selected skills with no skills and sparse routing; include oracle and wrong-sibling
> controls. Report residual failures, time/tokens and unknown evaluations. ML owns it.

H1 is tested identically, with the same statistic and interval method, for **two** frozen
contrasts (§2), neither swappable after data collection:

- **H1-a (headline adoption test):** condition B (sparse, shipped) vs condition A (no skills).
  This is the direct test of ADR-0024's hypothesis: does the system, as it ships today, change
  task outcomes at all. This is the contrast the "one minute/day" cost-model argument is about.
- **H1-b (promotion test):** condition C (contender) vs condition B (sparse). This is the test of
  whether whatever is being considered for broader rollout beyond bare sparse (a shadow dense
  profile, a composer variant — named in §2/§10, never "whichever wins") earns that promotion on
  real task outcomes, not only on retrieval metrics (DENSE-PROGRAM.md/E7.3 gates are necessary,
  not sufficient, for that decision).

Both are pre-registered as primary now; neither is chosen as "the" result after seeing which one
looks better (§6). Condition D (oracle) is reported against C as a **ceiling/headroom diagnostic**
only — it is not a deployable condition and is never scored as a gain/regression hypothesis.

**H2.** Paired time-to-completion and paired token cost, for the same two contrasts, each with a
95% paired-bootstrap interval on the mean delta (percentile method, matching
`tools/eval/dev_sparse.py`'s `bootstrap_paired_delta` — reimplemented stdlib-only in
`tools/pilot/analyze.py` so this pilot has no dependency on `tools/eval`). H2 has no direction
requirement pre-declared; a contender that is slower or costs more tokens while still passing H1
is a real, reportable trade-off, not a failure to hide.

**H3. The "one minute per developer per day" claim, mapped to measurable proxies.**
[ADR-0024](../adr/ADR-0024-target-architecture-tiers-flywheel-composer.md) "Cost model" states,
verbatim: *"if the system saves each active developer one minute a day (no hunting for the right
skill, no wrong-skill detour), 3 500 × 1 min × 21 days ≈ 1 225 hours/month ≈ \$98 k/month at
\$80/h... That minute is a hypothesis. E6.7 (paired pilot tasks) exists to measure it, and no
adoption claim is made before it does."* This pilot cannot observe "minutes per developer per
day" directly — it observes matched tasks. H3 maps the hypothesis onto what is observable:

| ADR-0024 mechanism | Pilot proxy | Operational definition | Data source |
|---|---|---|---|
| "no hunting for the right skill" | H1-a's paired Δtime (B − A) | mean paired time delta, sparse vs no-skills (H2's bootstrap output for contrast H1-a) | scoring sheet `time_seconds`, both conditions present |
| "no wrong-skill detour" | wrong-skill detour count | count of `skill_load_completed` events in a B/C run whose skill is not one later linked to a `helped` `skill_feedback` verdict or listed in that task's `expected_skills`, occurring before the first such relevant load | raw event ledger, joined by `task_id`/`load_id` (SEARCH-USE-TELEMETRY §4) — not the scoring sheet's summary `loads` count alone |
| loads that cost time/tokens but did not help | loads-never-used count | `skill_load_completed` events with no linked `skill_use_observed`/`skill_use_reported` and no `skill_feedback` by task end (SEARCH-USE-TELEMETRY §6: "exposed but unused") | raw event ledger; the scoring sheet's `loads` + `feedback_verdict` columns give only a coarse fallback (e.g. `loads > 0` with `feedback_verdict` in `{not_applicable, unknown}`) |
| "time to first relevant skill" | time-to-first-relevant-skill | elapsed time from `task_started` to the earliest `skill_load_completed` in the run whose skill is later linked to `helped` (or, absent feedback, to an observed/reported use) for that task; `unknown` if no such link exists | raw event ledger |

**The arithmetic that links them**, using the ADR-0024 cost-model shape directly so a future
report can substitute measured numbers for the hypothesized ones:

```
daily_minutes_saved  = (-mean_paired_delta_time_seconds[H1-a] / 60) * tasks_per_developer_per_day
monthly_hours_saved  = daily_minutes_saved * active_developers * working_days_per_month / 60
monthly_dollar_value = monthly_hours_saved * loaded_hourly_rate
```

`tasks_per_developer_per_day` is a **product assumption the pilot does not measure** — it is
distinct from ADR-0024's "≈80 agent prompts per developer per day" (a task is not a prompt); it
is a required placeholder (§10). `active_developers` and `loaded_hourly_rate` are the same
ADR-0024 assumptions (3 500 active developers, ≈$80/h), reused only for direct comparability, not
re-derived here.

**What would falsify H3** (any of these means this pilot does not support the one-minute
hypothesis, independent of whether it can *prove* the dollar figure — see §5 on what n that
would need):

1. H1-a's paired time-delta bootstrap interval (§2) includes 0 or is positive (condition B is not
   faster than condition A) — the mechanism ADR-0024 names does not show up as time saved.
2. Wrong-skill-detour rate and loads-never-used rate, measured within B/C, do not trend toward
   zero relative to the naive expectation that a working system mostly delivers what helps —
   i.e. the system is shown to *add* hunting rather than remove it.
3. H1 itself fails for contrast H1-a (gain rate does not exceed regression rate with the interval
   excluding 0) — time saved without a corresponding net success improvement does not establish
   the productivity benefit ADR-0024's arithmetic assumes (it assumes saved time is time not
   spent failing or redoing work, not time spent on a faster wrong answer).

A feasibility pilot (n = 20) that falsifies H3 on any of these is itself a usable, reportable
result — "the hypothesis did not survive its first measurement" is exactly what a frozen protocol
is for.

## 2. Design — conditions, pairing, and what is pinned per run

**Within-task, four named conditions**, each represented by a code used verbatim in
`task-bank.template.yaml`/`scoring-sheet.template.csv` and in `tools/pilot/analyze.py`:

| Code | Condition | What runs | Role |
|---|---|---|---|
| A | `no_skills` | SEARCH/USE fully disabled; the developer/agent solves the task unaided | floor baseline for H1-a |
| B | `sparse` | shipped tier-T1 profile, pinned `index_snapshot`/`router_version`/`policy_version` (SEARCH-USE-TELEMETRY §4 IDs), the corrected sparse ranking that is the current MVP-admitted comparator | "what ships today"; baseline for H1-a, comparator for H1-b |
| C | `contender` | **[PLACEHOLDER: named at freeze — e.g. "shadow hybrid profile, model identity X" or "E7.3 composer variant Y, admitted on dev by `all_required@4` per MVP §4 E7.3" — never "whichever wins," per §6]**, same pinned-version discipline as B | candidate for promotion; challenger for H1-b |
| D | `oracle` | the task's `expected_skills` (task-bank), force-delivered regardless of what search would return, permission-checked as normal | ceiling/headroom only; not a gain/regression hypothesis, not deployable |

**Pairing and assignment.** Each `(task, condition)` cell is run by a **distinct, single-use
developer/agent session**: no developer attempts the same task twice, so within-task learning
(remembering the answer from a prior condition) is not a confound — it is structurally impossible
by design, not merely discouraged. The scoring sheet's `order` column records that developer's
position in the *overall* pilot schedule (their 1st, 2nd, ... assignment across the whole pilot,
any task), not a position within one task's four conditions. Conditions are counterbalanced
across that schedule (e.g. a round-robin or randomized Latin-square assignment of condition to
schedule slot) so that time-of-day, day-of-week, environment drift or fatigue are not confounded
with condition. Record the exact assignment mechanism used at freeze time in place of this
sentence — it is part of what gets hashed in §13.

**Pinned per run**, recorded on every scored row and in the underlying event ledger
(SEARCH-USE-TELEMETRY §4): agent/model identity and version, harness/adapter identity and
version, `index_snapshot`, `router_version`, `policy_version`, and this protocol's
`protocol_sha256`. A run under a different pin than the one frozen for this pilot cohort is not
silently included — it is a different experiment and is excluded with a reason (§6).

**Not every task must reach all four conditions.** Developer availability across only
[PLACEHOLDER: 3 team names, §10] may leave some `(task, condition)` cells unrun. `tools/pilot/
analyze.py` only pairs a task into a contrast when both of that contrast's conditions were run
for it; coverage (§4, §11) reports how many bank tasks actually contributed to each contrast, so
a thin contrast is visible, never silently backfilled.

## 3. Task bank

Template: [`task-bank.template.yaml`](task-bank.template.yaml). Minimum **20** tasks, aim **40**
(MVP.md E6.7: "minimum 20, aim for 40"). Every task must satisfy **all** of:

- at least one real, published (or imminently publishable) skill plausibly applies to it;
- a developer, unaided, can plausibly close it in **≤ 60 minutes** (the task bank's
  `estimated_minutes` field, checked before inclusion, not after);
- a **pre-written acceptance check** exists before the task is ever run under any condition —
  deterministic wherever the work allows it (a test passing, a diff matching an expected shape,
  an exit code), a named evaluator role only where a deterministic check is genuinely impossible;
- it is real work requested by one of the **[PLACEHOLDER: 3 team names, §10]**, not authored to
  make any condition win — task selection is not part of the experiment being measured.

Excluded: tasks needing production access/secrets the pilot cannot safely grant; tasks whose only
plausible skill is still in draft/unreviewed; tasks a contributing team cannot spare a
developer-hour for across the conditions it will actually run under.

**No task is added, edited or removed after the task bank is frozen** (its own sha256, recorded
in `task-bank.template.yaml`'s `meta.frozen.task_bank_sha256`, itself covers the whole bank at
freeze time and is folded into the protocol's own `protocol_sha256`, §13). A task that turns out
to be unusable after freezing (access revoked, the relevant skill withdrawn, a team pulling out)
is **dropped, with a reason logged in `dropped_tasks` before its outcome under any condition is
known** — never quietly deleted from the list, and never dropped because an early condition's
outcome under it was unwelcome (§6). A dropped task lowers effective n; it is reported as dropped,
not backfilled with a replacement counted toward the same n.

Sampling: distribute tasks across the 3 teams; record `team` per task so a large or small
regression can be attributed rather than pooled into a single number that could be one team's
outlier (SEARCH-USE-TELEMETRY §6: "Compare within the same adapter, mode, rank/position and
cohort where possible").

## 4. Outcomes and recorded fields

Outcome is **success / failure / unknown**, decided by the task's pre-written acceptance check —
never by whether the developer felt good about the run. `unknown` is used, and reported, whenever
the check could not run to a terminal verdict (environment failure, timeout, withdrawn access);
it is **never coerced** to success or failure, and it is excluded from gain/regression counts
while still counting toward the row/coverage totals (`tools/pilot/analyze.py`'s
`n_excluded_unknown`, never silently absorbed).

Where the acceptance check needs a human judgement call, the **evaluator is blind to which
condition produced the run** wherever that is operationally possible (e.g. the transcript is
reviewed without the condition label visible); where blinding is not possible (an oracle run is
usually recognizable by its unusually direct skill delivery), that is stated per task, not
silently assumed away.

Recorded per `(task, condition)` row (`scoring-sheet.template.csv`): `task`, `condition`, `order`,
`developer_pseudonym`, `outcome`, `time_seconds`, `tokens`, `loads`, `feedback_verdict`
(SEARCH-USE-TELEMETRY §3 vocabulary: `helped`/`hindered`/`mixed`/`not_applicable`/`unknown`),
`evaluator`, `notes`. `notes` is free text and stays **local to the scoring sheet** — it is never
uploaded to the telemetry spool (§7); it exists for drop reasons, unknown-outcome reasons, and
pointers into usability think-aloud notes (§8).

## 5. Power and uncertainty

The statistic is the discordant-pair logic behind H1: among the `n` evaluable paired tasks for a
contrast, `m = n_gain + n_regression` are **discordant** (the two conditions disagree); the
remaining `n − m` are concordant and contribute nothing to the direction of the effect. Testing
H0: gain_rate = regression_rate is equivalent to testing whether the share of discordant pairs
that are gains, `p̂ = n_gain / m`, differs from 0.5 — the sign test / exact McNemar's test. Both
the discordant-pair **Wilson score interval** and the **exact (Clopper–Pearson)** interval on
`p̂` are computed by `tools/pilot/analyze.py` and mapped back onto the `diff = gain_rate −
regression_rate` scale via `diff = (m/n) · (2·p̂ − 1)`; both endpoints scale the same way.

**What difference is detectable, for n = 20 and n = 40**, at the boundary where the two-sided 95%
interval on `diff` just excludes 0 (computed, not assumed — reproducible with `tools/pilot/
analyze.py`'s `wilson_score_interval`/`clopper_pearson_interval`):

| n | assumed discordance | discordant pairs *m* | min net gain (Wilson) | min \|diff\| (Wilson) | min net gain (exact) | min \|diff\| (exact) |
|---:|---:|---:|---:|---:|---:|---:|
| 20 | 25% | 5 | — | *insufficient at any split* | — | *insufficient at any split* |
| 20 | 50% | 10 | 9 of 10 (net 8) | 0.40 | 9 of 10 (net 8) | 0.40 |
| 20 | 75% | 15 | 12 of 15 (net 9) | 0.45 | 12 of 15 (net 9) | 0.45 |
| 20 | 100% | 20 | 15 of 20 (net 10) | 0.50 | 15 of 20 (net 10) | 0.50 |
| 40 | 25% | 10 | 9 of 10 (net 8) | 0.20 | 9 of 10 (net 8) | 0.20 |
| 40 | 50% | 20 | 15 of 20 (net 10) | 0.25 | 15 of 20 (net 10) | 0.25 |
| 40 | 75% | 30 | 21 of 30 (net 12) | 0.30 | 21 of 30 (net 12) | 0.30 |
| 40 | 100% | 40 | 27 of 40 (net 14) | 0.35 | 27 of 40 (net 14) | 0.35 |

Read this as: with n = 20 and only a quarter of tasks discordant (5 pairs), **no possible split of
those 5 pairs clears the exact interval** — even a unanimous 5-for-0 split has an exact lower
bound of ≈0.478, short of 0.5 (the Wilson interval, less conservative at small samples, would
call that split significant; the exact interval would not — the reason this protocol requires
reporting *both*, and treats the exact interval as decisive when they disagree). At n = 20 the
pilot can only detect a fairly large, mostly-one-directional effect; at n = 40 with realistic
partial discordance it can detect a moderate one. **n = 20 is labelled a feasibility run, not a
powered study**, per MVP.md E6.7 ("minimum 20 ... as a feasibility study").

**An adoption claim needs an n computed from this pilot's own observed discordance — this pilot
does not compute that n for itself.** Standard normal-approximation sample size for a one-sample
proportion test (two-sided α = 0.05, 80% power; `z_{0.025} = 1.960`, `z_{0.20} = 0.842`):

```
m* = [ z_(α/2)·sqrt(0.25) + z_β·sqrt(p·(1−p)) ]^2 / (p − 0.5)^2
n* = m* / d̂
```
where `p` is the target share of discordant pairs that are gains (an ML/Product choice, made
once, before computing `n*` — not fit to whatever this feasibility pilot happened to observe),
and `d̂ = m_observed / n_observed` is **this pilot's measured discordance rate** for the contrast
in question. Reference values:

| target gain-share of discordant pairs (p) | m* (discordant pairs needed) | implied \|diff\| if fully discordant |
|---:|---:|---:|
| 0.60 | 194 | 0.20 |
| 0.65 | 85 | 0.30 |
| 0.70 | 47 | 0.40 |
| 0.75 | 29 | 0.50 |
| 0.80 | 19 | 0.60 |

Worked example: if the n = 20/40 feasibility pilot observes `d̂ = 0.40` (40% of pairs discordant)
for H1-a, and Product/ML set a target of `p = 0.70` (70% of discordant pairs should be gains to
call the system worth broad adoption), then `m* ≈ 47` and `n* = 47 / 0.40 ≈ 117` paired tasks
would be needed for a properly powered adoption study — **not the 20–40 this feasibility pilot
runs.** This arithmetic, with this pilot's actual `d̂` substituted in, belongs in the reporting
template (§11), not a separate later negotiation.

## 6. Stop rules and forbidden moves

Mirroring DENSE-PROGRAM.md §4a's multiplicity discipline, applied to tasks and outcomes instead
of retrieval variants:

- **No re-running a condition.** A `(task, condition)` cell is run once. `tools/pilot/
  analyze.py` refuses to analyze a scoring sheet containing a duplicate `(task, condition)` row
  (`DuplicateRunError`) rather than silently keeping the first, last, or best of the two.
- **No post-hoc task removal.** A task included in the frozen bank stays in the denominator
  unless formally dropped *before* its outcome is observed, with a reason (§3). Dropping a task
  because its result was inconvenient is exactly the failure mode this rule exists to prevent.
- **No switching the primary outcome.** H1-a and H1-b (§1) are both primary from the start; the
  report never elevates a secondary/diagnostic number (H2, H3, or oracle headroom) to replace a
  primary result that came out unfavorably.
- **One analysis per frozen protocol version.** `tools/pilot/analyze.py` refuses to run against a
  scoring sheet whose header does not carry this protocol's frozen `protocol_sha256` (§13). A
  protocol amendment that changes the outcome rule, the conditions or the contrasts is a new
  version with its own sha and, if data collection has already started under the old version,
  its own separate task bank — not a silent re-analysis of the same data under new rules.
- Every dropped task, every excluded-unknown pair, and every duplicate rejected is counted and
  shown (§11) — running k tasks and reporting the best-looking subset without saying k is exactly
  what DENSE-PROGRAM.md §4a's rule 3 exists to prevent on the retrieval side; the same applies
  here to tasks.

## 7. Data handling

Per [SEARCH-USE-TELEMETRY.md §5](../SEARCH-USE-TELEMETRY.md):

- **No prompt text.** Task descriptions and transcripts are not part of the telemetry spool; only
  IDs, outcome codes, timings, token counts, skill revisions and feedback verdicts leave a
  developer's session. The scoring sheet's free-text `notes` column stays local to the pilot's
  private working set, never uploaded.
- **Pseudonymous principals.** `developer_pseudonym` is a rotating tenant-scoped keyed HMAC, per
  §5; it is not anonymous, and cross-month pseudonym comparisons are labelled incomparable if the
  pilot spans a key rotation.
- **Cohort-level reporting, no individual ranking.** §11's reporting template shows populations
  and aggregate rates; it never attributes a specific outcome to a named developer outside the
  pilot's own private working notes, and never ranks developers against each other.
- **Consent line for the redacted evaluation corpus** (§5: "Curated evaluation examples require
  separate redaction and consent/organization policy"). Template text, to be reviewed and
  finalized by Product/Legal before the first task runs (this exact wording is itself frozen at
  the same time as the rest of this document — §13):

  > *"By taking part in this pilot task, you agree that your outcome (success / failure /
  > unknown), timing, token counts, skill loads and feedback verdict for this task are recorded
  > under a pseudonymous, rotating identifier (SEARCH-USE-TELEMETRY.md §5); no prompt text or
  > file content you write is retained. If this episode is selected for the redacted evaluation
  > corpus used to improve retrieval quality, [PLACEHOLDER: Legal/Product-approved redaction and
  > opt-in process — not specified by this protocol] applies before any excerpt leaves the
  > pilot's private working set. You may withdraw this task's data before [PLACEHOLDER:
  > withdrawal deadline] by [PLACEHOLDER: contact/process]."*

## 8. Usability sessions

**3 teams** — the same **[PLACEHOLDER: 3 team names, §10]** contributing tasks — hands-on,
think-aloud sessions on **real tasks** (not the paired-condition tasks of §2–§4; a separate,
smaller set chosen for observability of the whole workflow), per MVP.md §3's Usability row:

> Task-based pilot covers discovery, loading, following instructions, dependencies, tool
> permissions/compatibility, stale instructions and feedback; report failures and unknowns, not
> one opaque score.

**What is recorded**, per stage, coded `ok` / `failure` / `unknown` with a short observer note
(kept local, per §7 — never uploaded verbatim): discovery (did the developer find a relevant
skill unaided), loading (did hydration complete without error), instruction-following (did the
developer follow the skill's steps as written, and if not, why), dependencies (did required
skills resolve, `cannot_fit` if not), tool permissions/compatibility (did the environment support
what the skill assumed), staleness (did the developer hit outdated instructions or a deprecated
reference), feedback (what verdict, if any, the developer gave).

**How it is reported**: one count per stage category across the 3 sessions (e.g. "discovery: 2
ok / 1 failure / 0 unknown"), never collapsed into a single usability score — MVP.md §3 is
explicit that "report failures and unknowns, not one opaque score" is the acceptance bar, and
SEARCH-USE-TELEMETRY §6 forbids treating low usage or an absent negative as proof of anything.
Reasons route to owners the same way SEARCH-USE-TELEMETRY §7 already defines
(`wrong_match`→ranking, `unclear_steps`→text, `missing_prerequisite`→dependencies,
`stale`→revision, `incompatible_environment`→compatibility, `excess_context`→budget,
`load_failed`→delivery) so a usability finding routes to an owner, not a vague impression.

## 10. Placeholders the product owner must fill

This protocol deliberately leaves the following undecided rather than guessing at them; none of
them may be filled in by inference from partial pilot data, and all must be set **before**
freezing (§13):

1. **Team names** — the 3 pilot teams contributing tasks and usability sessions (§3, §8; also
   `task-bank.template.yaml`'s `meta.teams`).
2. **Dates** — the freeze sign-off date (§13, this document's Status line), the pilot's start/end
   window, and the withdrawal deadline in the consent line (§7).
3. **The contender's identity** — condition C (§2): the exact profile, model/router/policy
   version under evaluation for promotion (shadow hybrid, an E7.3 composer variant, or otherwise)
